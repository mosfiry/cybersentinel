### Microsoft API references for the next diagnostic

The [Microsoft Learn LPAC verification answer](https://learn.microsoft.com/en-sg/answers/questions/6022970/supported-win32-method-to-verify-lpac-identity-bef) says public Win32 documentation does not define a class-specific `GetTokenInformation(TokenIsLessPrivilegedAppContainer)` output contract, advises against making a security decision from it, and suggests a distinct-ACE `AccessCheck` semantic cross-check: grant one access bit to `ALL_APPLICATION_PACKAGES` (`S-1-15-2-1`) and a different bit to `ALL_RESTRICTED_APPLICATION_PACKAGES` (`S-1-15-2-2`); expected grants are both bits for a regular AppContainer and only the restricted-packages bit for an LPAC. It explicitly cautions that this composition is not a documented `IsLPAC` API and should be validated on the target system.

The official [`AccessCheck`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-accesscheck) contract requires an impersonation token with `TOKEN_QUERY`; `MAXIMUM_ALLOWED` returns the granted mask, and the security descriptor must include owner and group SIDs. [`DuplicateToken`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-duplicatetoken) requires `TOKEN_DUPLICATE` on the primary token and creates an impersonation token with `TOKEN_QUERY` and `TOKEN_IMPERSONATE`. The paired LPAC/ordinary-AppContainer differential remains unimplemented and must not be treated as proven until it passes on Windows.
