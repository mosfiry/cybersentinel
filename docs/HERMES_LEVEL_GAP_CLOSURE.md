## Verification

The Owner observability API and Desktop tab validate and combine the plan-action graph with the separate specialist-analysis graph. The current stage includes the matching specialist task status when present, while the projection exposes only bounded task/agent identities, statuses, dependencies, error categories, and opaque evidence references; it never returns provider response or proposal bodies. This exposes recorded specialist activity without implying parallel execution of mission tools.

The evaluation summary is a separate Owner+CSRF-protected read-only Mission endpoint and a compact panel within observability. It reads only a pre-existing `agent_evaluations.sqlite3`, emits the ten fixed metric dimensions and finite stored values, and hashes evidence IDs into Owner/Mission-bound opaque references only after the complete evidence chain and exact Mission receipt validate. The store does not persist an evaluation verdict, so the API reports `not_persisted`; it neither computes a verdict nor synthesizes a run when no records exist. The production Mission workflow does not currently write evaluation runs.

At the prior checkpoint, the full Python suite completed with **1,389 passed and 1 skipped**; the MCP pre-push `pytest -q` checkpoint completed with **1,417 passed, 1 skipped, and 4 warnings**. Desktop syntax checks (`npm run check` and `node --check ../web/app.js`) and the Node/Electron suite completed with **9 passed**. Browser and pinned-HTTP tests completed with **22 passed** (`pytest -q tests/test_browser_tools.py tests/test_pinned_http.py`), including assertions that the Chromium OS sandbox is explicitly enabled and POSIX root execution is refused. The Linux packaged-resource smoke launched the copied Playwright-managed Chromium resource with sandboxing enabled and reported version `151.0.7922.34`. The focused specialist-memory/provider and AgentGraph tests previously completed with **41 passed**; Mission observability and public-web Owner/CSRF tests with **33 passed**; and evaluation projection/store/public-boundary tests with **40 passed**. `python3 -m compileall` and `git diff --check` reported no errors. A redacted high-confidence credential-pattern scan of all 11 changed files reported no matches and did not print values. Focused counts overlap with the full suite and must not be added together. The Browser/Registry integration test's authorization/fence/evidence/effect-ledger doubles establish control flow only; the real Chromium tests use controlled localhost pages, not production websites or a fully authenticated user session.

The specialist tests use deterministic provider doubles. They prove production control flow, exact provider/model binding/no fallback behavior, bounded task-scoped prompts, scope/fence validation, concurrency, result validation, cancellation handling, and fail-closed no-replay recovery only. They do **not** prove actual provider endpoint availability, real local Qwen inference, model output quality, live production Mission behavior, or Windows acceptance. Provider requests are not interrupted mid-call; cancellation discards the response after it returns. Owner Skill service, public bridge, and inert-rendering tests exercise list/detail, evidence-backed candidate qualification, explicit approval/revocation, Mission selection, CSRF/Owner boundaries, and hostile text rendering; they do not prove executable Skill procedures or native desktop/product acceptance. Mission observability and evaluation-summary tests cover bounded Owner-only reads, exact Mission/Owner isolation, evidence-chain verification, stable denial/no-run behavior, and safe text rendering. They do not establish production evaluation-run creation, a stored or accepted policy verdict, end-to-end Windows or Owner acceptance, live search availability or live MCP-server acceptance, broad Browser public-target acceptance, all requested product APIs/UI, or Hermes-level completeness.
