This is an incremental implementation branch, **not** complete Hermes-level parity, not proof that the broader definition of done is met, and not authorization for a final v5.2.0 release. The immutable v5.1.0 release is to remain unchanged.

The matrix separates code that is operational in the current implementation from the extent of test evidence and capabilities that remain missing or unaccepted. “Operational” does not imply Windows, live-service, production deployment, real-model, or user-facing product acceptance.

## Verification

The Owner observability API and Desktop tab validate and combine the plan-action graph with the separate specialist-analysis graph. The current stage includes the matching specialist task status when present, while the projection exposes only bounded task/agent identities, statuses, dependencies, error categories, and opaque evidence references; it never returns provider response or proposal bodies. This exposes recorded specialist activity without implying parallel execution of mission tools.

The evaluation summary is a separate Owner+CSRF-protected read-only Mission endpoint and a compact panel within observability. It reads only a pre-existing `agent_evaluations.sqlite3`, emits the ten fixed metric dimensions and finite stored values, and hashes evidence IDs into Owner/Mission-bound opaque references only after the complete evidence chain and exact Mission receipt validate. The store does not persist an evaluation verdict, so the API reports `not_persisted`; it neither computes a verdict nor synthesizes a run when no records exist. The production Mission workflow does not currently write evaluation runs.

The latest full repository-wide Python regression completed with **1,389 passed and 1 skipped** (`pytest -q`). Desktop syntax checks (`npm run check` and `node --check ../web/app.js`) and the Node/Electron suite completed with **9 passed**. Browser and pinned-HTTP tests completed with **22 passed** (`pytest -q tests/test_browser_tools.py tests/test_pinned_http.py`), including assertions that the Chromium OS sandbox is explicitly enabled and POSIX root execution is refused. The Linux packaged-resource smoke launched the copied Playwright-managed Chromium resource with sandboxing enabled and reported version `151.0.7922.34`. The focused specialist-memory/provider and AgentGraph tests previously completed with **41 passed**; Mission observability and public-web Owner/CSRF tests with **33 passed**; and evaluation projection/store/public-boundary tests with **40 passed**. `python3 -m compileall` and `git diff --check` reported no errors. Focused counts overlap with the full suite and must not be added together. The Browser/Registry integration test's authorization/fence/evidence/effect-ledger doubles establish control flow only; the real Chromium tests use controlled localhost pages, not production websites or a fully authenticated user session.

The specialist tests use deterministic provider doubles. They prove production control flow, exact provider/model binding/no fallback behavior, bounded task-scoped prompts, scope/fence validation, concurrency, result validation, cancellation handling, and fail-closed no-replay recovery only. They do **not** prove actual provider endpoint availability, real local Qwen inference, model output quality, live production Mission behavior, or Windows acceptance. Provider requests are not interrupted mid-call; cancellation discards the response after it returns. Owner Skill service, public bridge, and inert-rendering tests exercise list/detail, evidence-backed candidate qualification, explicit approval/revocation, Mission selection, CSRF/Owner boundaries, and hostile text rendering; they do not prove executable Skill procedures or native desktop/product acceptance. Mission observability and evaluation-summary tests cover bounded Owner-only reads, exact Mission/Owner isolation, evidence-chain verification, stable denial/no-run behavior, and safe text rendering. They do not establish production evaluation-run creation, a stored or accepted policy verdict, end-to-end Windows or Owner acceptance, live search availability, MCP, broad Browser public-target acceptance, all requested product APIs/UI, or Hermes-level completeness.

## Mission-scoped WebResearch continuation (2026-10-05)

The `web_research` ToolRegistry action is Owner-only and Mission-scoped, and it is dispatched through the existing canonical `ExecutionContext`, authorization decision, persisted Mission authorization, Scope Resolver, execution fence, and strict Mission evidence chain. It sends only a scrubbed query to the existing Web Search provider, checks every discovered URL against the exact current Owner/Mission scope, fetches only authorized `GET` pages over the existing DNS-pinned transport without following redirects, and returns bounded visible-text excerpts. Each successful page produces an explicitly untrusted evidence record with retrieval time, URL, raw/excerpt digests, source/query/scope provenance, and exact Mission/task/execution binding. Factual confidence remains `not_assessed`; no raw query, provider error body, page HTML, or credential is persisted. The allowed-tool schema is 15,081 serialized characters against the default 16,000-character cap.

The focused WebResearch tests completed with **7 passed**; the authorized WebResearch-through-ToolRegistry path also passed in the controlled Chromium/localhost integration test. Compilation and diff-whitespace checks passed. The public search provider's last live response remains HTTP 202 anti-automation; deterministic search-provider tests plus a pinned localhost fetch do **not** establish live public-web, authenticated end-user, Windows, or local-Qwen acceptance. Search/fetch outside the exact authorized Mission target, independent factual verification, and model-generated synthesis remain unsupported.
