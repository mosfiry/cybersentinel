# Hermes-Level Gap Closure

This is an incremental implementation branch, **not** complete Hermes-level parity, not proof that the broader definition of done is met, and not authorization for a final v5.2.0 release. The immutable v5.1.0 release is to remain unchanged.

The matrix separates code that is operational in the current implementation from the extent of test evidence and capabilities that remain missing or unaccepted. “Operational” does not imply Windows, live-service, production deployment, real-model, or user-facing product acceptance.

## Verification

The Owner observability API and Desktop tab validate and combine the plan-action graph with the separate specialist-analysis graph. The current stage includes the matching specialist task status when present, while the projection exposes only bounded task/agent identities, statuses, dependencies, error categories, and opaque evidence references; it never returns provider response or proposal bodies. This exposes recorded specialist activity without implying parallel execution of mission tools.

The final repository-wide Python suite completed with **1,365 passed and 1 skipped** (`pytest -q`). Desktop syntax checks (`npm run check` and `node --check ../web/app.js`) and the Node/Electron suite completed with **7 passed** (`cd desktop && npm run check && node --check ../web/app.js && npm run test:desktop`). The final focused specialist-memory/provider and AgentGraph tests completed with **41 passed** (`pytest -q tests/test_provider_bound_specialists.py tests/agent_intelligence/test_graph.py`); the focused observability API/security tests completed with **32 passed** (`pytest -q tests/test_mission_observability.py tests/test_public_web_boundary.py`). `python3 -m compileall` and `git diff --check` reported no errors. Focused counts overlap with the full suite and must not be added together.

The specialist tests use deterministic provider doubles. They prove production control flow, exact provider/model binding/no fallback behavior, bounded task-scoped prompts, scope/fence validation, concurrency, result validation, cancellation handling, and fail-closed no-replay recovery only. They do **not** prove actual provider endpoint availability, real local Qwen inference, model output quality, live production Mission behavior, or Windows acceptance. Provider requests are not interrupted mid-call; cancellation discards the response after it returns. Owner Skill service, public bridge, and inert-rendering tests exercise list/detail, evidence-backed candidate qualification, explicit approval/revocation, Mission selection, CSRF/Owner boundaries, and hostile text rendering; they do not prove executable Skill procedures or native desktop/product acceptance. Mission observability tests verify the bounded Owner-only API, specialist/action graph projection, event wiring/projection, stable denial behavior, and safe text rendering, not end-to-end Windows or Owner acceptance. The suite does not prove live search availability, Windows installation, browser/MCP, all requested product APIs/UI, or Hermes-level completeness.

## Release boundary

Do not rewrite or retag immutable `v5.1.0` and do not claim `v5.2.0` production completion based on this branch. Any later release decision still requires its full CI, desktop/Windows, runtime, real-model, and Owner acceptance gates.
