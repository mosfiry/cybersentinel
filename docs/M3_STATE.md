### V6 — External-effect ledger and idempotency

Implemented in code commit `375a55c4fb0e094417a50a374d12f90db3c77352`. `agent/external_effects.py` stores write-ahead `PLANNED`, `RESERVED`, `DISPATCHED`, and terminal/recovery outcomes in the same rollback-journal queue database. State history is protected by SQLite update/delete triggers. Effect identity is deterministic across worker restarts and binds mission/task/version/execution/request/provider plus tool/version/argument digest and hashes of target, scope, workspace, network, and credential boundaries; raw arguments, results, or scope context are not stored. WAL mode is rejected because it cannot satisfy the required shared-store transaction contract.

The canonical `ToolRegistry` now requires provider metadata for every `network-read`, `state-write`, and `bounded-exec` tool. Every provider-backed dispatch requires a live `ExecutionFence` and explicit `MissionAuthorizationSnapshot`; reservation, dispatch, and outcome writes revalidate that fence. Duplicate or changed-intent replays are blocked. Timeouts, ordinary handler exceptions, process death after dispatch, and `UNKNOWN` outcomes are quarantined as recovery-required; a confirmed `FAILED` outcome is permitted only when the provider call was provably cancelled before dispatch. Registered handlers currently advertise no provider idempotency support, so no exactly-once behavior is claimed and no ambiguous call is automatically replayed.

Adversarial coverage in `tests/test_external_effect_ledger.py` exercises stale/wrong fences, changed payload and scope, duplicate and concurrent reservations, crashes between `PLANNED` and `RESERVED`, timeouts and late results, unknown-state history, append-only event enforcement, WAL rejection, secret-free persistence, and the missing-authorization gate.
