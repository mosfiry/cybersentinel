### V2 — Durable worker identity and lease generation

Implemented in code commit `8a6990a0ed6657d8368d8d1448126f9f11a65467`. `MissionQueue` now migrates in a durable `mission_worker_generations` registry; registration increments a stable logical worker's generation transactionally and allocates a unique process-instance ID. Queue rows carry both instance ID and runtime generation alongside the existing monotonic lease epoch. Claim, heartbeat, update, and release operations verify the registered current generation inside `BEGIN IMMEDIATE` and bind mutations to the exact worker instance, logical owner, generation, lease epoch, and live expiry. A restart supersedes earlier generations; graceful supervisor exit retires its generation without prematurely releasing a live lease. Low-level legacy queue APIs remain compatible for unregistered historical callers; execution-path unification and eliminating bypasses are V3's scope.

Adversarial coverage in `tests/test_worker_generations.py` and the updated same-logical-ID stale completion case verifies monotonic generation after database reopen, stale claim/heartbeat/update/release rejection, queue-row immutability, and supervisor retirement. Focused tests passed **33/33**; the complete suite passed **793 passed, 1 skipped**; `py_compile`, `compileall`, `git diff --check`, and a changed-path boundary-aware secret scan passed.

The same contract is threaded through MissionWorker claim/heartbeat/dispatch/completion/release/retirement, MissionRuntime save/dispatch, AgentCore deterministic and native-model tool routes, MissionStore execution saves, EvidenceChainStore append, and mission-bound ToolRegistry dispatch. Queue mutations validate the fence in their SQLite write transaction. Strict bridge/AgentCore execution configurations fail closed; the registry rejects mission-bound calls with a missing fence before invoking a handler. Strict runtime control-plane Owner-decision and ambiguous-effect reconciliation calls now fail closed until their authorized V7/V8 workflows exist. `ExecutionFence.assert_effect_reservation()` is available for V6; no external-effect ledger existed to integrate yet.
