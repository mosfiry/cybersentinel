# Tool Model

The canonical registry in `tools/registry.py` is authoritative. This branch contains 16 tools; each `ToolSpec` carries its input/output schemas, risk class, required authorization, scope requirements, handler, network/filesystem/process/credential access labels, timeout, and evidence requirements. `build_registry()` validates these fields against controlled vocabularies before registration. The registry—not this document or model output—defines executable capability; this is the only tool registry.

## Uniform metadata and execution

The canonical `ToolSpec` schema includes `risk_class`, `network_access`, `filesystem_access`, `process_access`, `credential_access`, `requires_owner`/`owner_only`, `scope_required` and named scope constraints, input/output schemas, handler, evidence requirements, timeout, and effect/idempotency metadata. Registry validation rejects unknown access labels, missing or malformed evidence labels, incomplete scope requirements, invalid timeout values, and inconsistent process/scope combinations. `ToolSpec.timeout` is the single canonical per-tool timeout source; MissionRuntime may further lower it with the active Mission budget. No secondary dispatch or timeout registry is used.

Access labels distinguish allowlisted provider traffic from DNS-pinned Mission-scoped network tools. Application database/evidence writes remain governed by risk, Mission ownership and evidence policy; they are not mislabeled as arbitrary path-level filesystem access. The legacy `run_project_tests` process is deliberately labeled `host_process_unscoped` / `host_fs_via_process` / `workspace_process_unisolated` / `host_user_credentials_possible`; those labels reveal current reach, not safe confinement. Production Browser, WebResearch and MCP dispatch retain their existing Owner/Mission, Scope Firewall, ExecutionContext, execution-fence, effect-ledger and evidence checks. Remote/page content remains untrusted data.

The six current string-input tools are `search`, `watch`, `unwatch`, `run_project_tests`, `red_team_assess`, and `scoped_http_probe`. Each uses a canonical JSON object schema with one required string field, no extra properties, and a maximum argument length of 256 characters; handlers and scope policies impose additional tool-specific constraints. The five structured-object tools are `browser`, `browser.fill`, `web_research`, `mcp.discover`, and `mcp.invoke`; they carry explicit bounded schemas. The other five tools accept no arguments. A plan may contain no more than eight tools. The 16,000-character context tool-schema budget measures `model_tool_definitions()`—the exact canonical function schemas sent to a provider—not duplicated local `parameters`/`input_schema` aliases or policy metadata. Unknown tools, unexpected arguments, null values, malformed arrays, and oversized strings are rejected by deterministic code before execution. For `mcp.invoke`, the generic registry schema is followed by a second runtime validation against the exact freshly discovered remote input schema before any remote call.

MCP has only two canonical wrapper tools; remote server tool names are **not** added as arbitrary executable `ToolSpec`s. The Owner+Mission trust store and per-tool schema approval gate decide which remote revision `mcp.invoke` may reach. Discovery, trust, and invocation constraints are documented in [`docs/architecture/MCP.md`](architecture/MCP.md).

## Coverage gaps

Browser automation, Mission-scoped WebResearch, and the bounded MCP client are registered through this canonical ToolRegistry. `run_project_tests` is only a fixed pytest wrapper and is not a secure general terminal. No generic filesystem read/write tool, `git` tool, or archive tool is registered. The general ToolSpec metadata layer is now uniform and validated, but the complete requested filesystem/terminal/git/archive/code-execution capability set is **not implemented**. Priority 5 must replace or disable the unisolated test subprocess before claiming sandboxed execution; Linux, Windows and user-facing acceptance remain separate gates.

The model is a planner, not an authorization authority. Tool execution is selected from the registry; model output cannot create a new executable tool. Owner authentication, scope authorization, execution fences, effect-ledger reservations, and per-tool risk policy are checked by the runtime, not inferred from the model's proposal.
