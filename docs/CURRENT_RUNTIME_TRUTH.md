## Runtime, authority, and evidence boundaries

Browser chat (`POST /api/public/chat`), internal chat (`POST /api/chat`), and the legacy-named `/api/command` path converge on `api.chat.chat → AgentCore → MissionRuntime`. `/api/tasks` retains a compatibility `Task` envelope but persists and controls canonical missions through `MissionTaskAdapter`. `AgentTaskRuntime`, `AgentRuntime`, `AgentLoop`, and `core.engine` remain compatibility/test surfaces rather than the current browser/API mission path.

Owner authority comes from server-side username/password authentication. The public CSRF session is not Owner authority; the browser Owner session is an HttpOnly cookie, and internal clients use the separate bridge transport credential. Missions, conversations, and mission-backed Tasks are Owner-scoped. **Owner Instruction is the highest application authority within the authenticated delegation, but never overrides immutable system or security boundaries.** Model output, tool proposals, external data, and generic success booleans remain untrusted. Deterministic policy, typed authorization, the signed mission snapshot, scope checks, and a one-use execution proof are enforced before registry dispatch; the live Owner session is checked again immediately before serial and parallel tool handlers run, so revocation during model inference blocks dispatch. Invalid or unavailable tool schemas fail closed.

Tool output, model text, and Owner reconciliation choices do not establish goal completion. Completion requires system-issued evidence for supported criteria, deterministic verification, and a valid mission completion proof. The Findings UI displays only system-evidenced records; there is no separate persisted `Finding` entity.

The authenticated Product Workspace is mission-bound and read-only. File listings, reads, and fixed Git views deny sensitive paths case-insensitively; Git diff uses explicit path exclusions and remote credentials are redacted. Commit, push, and arbitrary shell actions are not exposed.

## Integrated and tested capabilities

The browser exposes high-level `fast`/`balanced`/`deep`/`local` orchestration preferences rather than provider or exact model IDs; legacy explicit-profile selection remains available to API clients. Authenticated chat and Mission/Task execution route inference through `CyberSentinelMind` and capability-driven `ModelOrchestrator`. This local product capability is not evidence that a live provider is configured or reachable. Tool schemas remain constrained and fail closed rather than granting a model authority through metadata or malformed proposals.

A callback-claim barrier coordinates pause/cancel controls with callback claiming. Owner-scoped validated experience can carry evidence-backed material from Mission A into Mission B, where it is explicitly surfaced as **untrusted context** with retrieval receipts rather than promoted to verified truth. The shared sanitized Mind context carries Mission/Task and durable ReasoningCase state, hypotheses, verified-evidence and counter-evidence references, authorized scope/tool bounds, memory, knowledge, observations, and recent Owner conversation. Capability-declared analyst/reviewer/synthesis roles run within profile/call/token/deadline budgets and optional known-cost ceilings; a separately configured Critic returns a strict-schema diagnostic only. Each model invocation records safe request/mission/task provenance, role, hashes, UTC timestamp, latency, explicit token-usage source, and a cost estimate only when a declared rate and known usage exist. Hash-chain events retain model/context hashes and role provenance. Model text and critic reports are never evidence or authorization. The existing deterministic critic remains structural; it is **not** a semantic truth or independent vulnerability verifier.

One Research Specialist is integrated through the same MissionRuntime, router, Owner authority, and tool scopes; its eligible native model turn uses the Mind adapter after the existing role, Owner, scope, and task-tool intersections. It does not create a parallel authority/runtime path. `scoped_http_probe` is a bounded, scope-authorized HTTP **GET** capability: redirects are blocked, credentials are not sent, and response bodies are not returned; the tool reports bounded metadata and a SHA-256 digest. This final verification did not contact a live target. General-web search remains unavailable/not implemented; GitHub repository search, where configured, is a separate capability.

The supervised SQLite queue atomically limits active entries to 10 by default and rejects overflow as `mission_queue_full` (HTTP 429). The worker processes one mission slice at a time, renews its lease during blocking model/tool calls, recovers expired leases, and preserves ambiguous in-flight effects for Owner reconciliation rather than replaying them blindly. `PlanStep` prerequisites are validated for duplicate IDs, missing steps, and cycles; execution waits for ready predecessors. Non-empty top-level `Plan.dependencies` and cross-mission dependency scheduling are not supported.

The persistent scheduler supports **one-time dispatch only** and rejects recurring `interval_seconds` and nonzero scheduled `retry_limit`; it does not create fresh recurrence executions or retry failed schedule dispatches. The current one-shot implementation is **not verified safe for timestamp ordering or dispatch handoff**: `run_at` is stored as an unchecked string, due selection compares SQLite text values lexically rather than normalized instants, and offset timestamps can therefore be ordered incorrectly. Dispatch enqueues into the queue database and only afterward marks the schedule complete in a separate scheduler-database update. A crash between those writes leaves the schedule eligible for redispatch; replay can reset an existing non-executing queue item and its attempt count because `enqueue` upserts it. The current tests cover one UTC one-shot dispatch and rejection of recurrence/retry settings, but do not cover offset/invalid timestamp inputs, reopening after restart, or an injected failure in the dispatch handoff. Timestamp normalization, handoff idempotency, and restart/crash behavior remain unverified; **do not describe dispatch as crash-safe**. This restriction is about scheduled jobs and does not erase separately bounded mission-recovery behavior. No recurring scheduling or cross-mission dependency work is in scope absent a new requirement.

## Owner-approved rules and remaining security gates

Use **two Owner-authorized test accounts and synthetic data by default**. Real data requires explicit scope and authorization. LLMs explain only; a deterministic, evidence-based verifier must decide whether a vulnerability is established.

A complete replayable request/response evidence chain remains required: each message/exchange must record method, URL, headers, request body, status, response headers and body, timestamps, synthetic/test-account identity, and request ID, with SHA-256 digests per message/exchange. New writes now use a best-effort pattern redactor at Mission, Evidence Chain, durable-memory, application-log, and lifecycle-log boundaries; recognizable credential fields/forms are redacted before persistence, safe technical fields and opaque `secret_ref` references are retained, and affected hashes are recomputed. This does not detect arbitrary unlabelled secrets, does not retroactively scrub old database rows, and is not an encrypted Vault. Actual credentials, cookies, and tokens still require a separate encrypted, access-controlled Vault retained until the Owner manually deletes them.

### Owner-approved data, Vault, synchronization, and execution requirements — NOT IMPLEMENTED

All mission data and artifacts must be kept as organized, classified local files with Owner-only filesystem permissions. Ordinary mission files are not encrypted at rest; Vault secrets are the exception. The Owner retains data until manually deleting it.

All data must be available across devices through direct peer-to-peer transfer over the Owner's own VPN or another directly reachable connection. There must be no central data server, rendezvous service, or relay. If no direct route exists, synchronization waits until direct connectivity becomes available and must not fall back to a centralized path.

The required architecture has a **Computer Vault** using the local Computer Keychain and a **Phone Vault** using Android Keystore. Encrypted secret copies synchronize peer-to-peer under the same direct-route rule. Routine Owner access uses username/password login; successful Owner authentication makes that device trusted. Emergency recovery uses an offline recovery key kept by the Owner only, not a central recovery service or KMS. Login and device trust do not grant blanket external-target permission: full access means the capabilities within the current explicit Owner delegation.

For normal replay, only after Owner, Tool, and scope validation, the authorized mission Worker/Sandbox may decrypt a referenced secret on demand in memory and pass it straight to the isolated HTTP client. Erasure afterward is best-effort. Secret values must never enter logs, stdout, databases, Evidence Chain, or Mission history. The replayable Evidence Chain records the HTTP fields and SHA-256 per message/exchange, and uses `secret_ref` only for secret-bearing values.

These are Owner-approved target requirements, **not implemented today**. The current repository has no local-file organization/permission implementation for this requirement, Computer Vault, Phone Vault, direct peer-to-peer synchronization or no-route waiting behavior, offline recovery-key flow, worker secret resolver, or authenticated two-synthetic-account BOLA/IDOR test flow. These requirements do not relax non-bypassable authentication, authorization, scope, platform, or system safeguards.

The following critical items are **not implemented**: a full manual program-authorization capture/approval record bound to the Owner session and scope; the local-file organization/permission behavior, Computer/Phone Vaults, direct peer-to-peer sync and no-route wait behavior, login-based device trust, offline Owner-only recovery-key flow, worker secret resolver, and `secret_ref` access grants; an authenticated two-synthetic-account BOLA/IDOR test flow; the complete replayable HTTP evidence chain with secret values excluded; a deterministic independent vulnerability verifier; persisted `Finding`; a review-ready report; and an explicit Owner-approval workflow before disclosure. There is currently **no disclosure path**. Scope validation and the bounded probe do not substitute for these gates.
