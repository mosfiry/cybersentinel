## Runtime, authority, and evidence boundaries

Browser chat (`POST /api/public/chat`), internal chat (`POST /api/chat`), and the legacy-named `/api/command` path converge on `api.chat.chat → AgentCore → MissionRuntime`. `/api/tasks` retains a compatibility `Task` envelope but persists and controls canonical missions through `MissionTaskAdapter`. `AgentTaskRuntime`, `AgentRuntime`, `AgentLoop`, and `core.engine` remain compatibility/test surfaces rather than the current browser/API mission path.

Owner authority comes from server-side username/password authentication. The public CSRF session is not Owner authority; the browser Owner session is an HttpOnly cookie, and internal clients use the separate bridge transport credential. Missions, conversations, and mission-backed Tasks are Owner-scoped. **Owner Instruction is the highest application authority within the authenticated delegation, but never overrides immutable system or security boundaries.** Model output, tool proposals, external data, and generic success booleans remain untrusted. Deterministic policy, typed authorization, the signed mission snapshot, scope checks, and a one-use execution proof are enforced before registry dispatch; invalid or unavailable tool schemas fail closed.

Tool output, model text, and Owner reconciliation choices do not establish goal completion. Completion requires system-issued evidence for supported criteria, deterministic verification, and a valid mission completion proof. The Findings UI displays only system-evidenced records; there is no separate persisted `Finding` entity.

The authenticated Product Workspace is mission-bound and read-only. File listings, reads, and fixed Git views deny sensitive paths case-insensitively; Git diff uses explicit path exclusions and remote credentials are redacted. Commit, push, and arbitrary shell actions are not exposed.

## Integrated and tested capabilities

The integrated runtime includes an Owner-facing model catalog, model pinning, and automatic routing within the existing model/router path. This is a local product capability, not evidence that a live provider is configured or reachable. Tool schemas are constrained and fail closed rather than granting a model authority through metadata or malformed proposals.

A callback-claim barrier coordinates pause/cancel controls with callback claiming. Owner-scoped lexical memory can carry evidence-backed material from Mission A into Mission B, where it is explicitly surfaced as **untrusted context** rather than promoted to verified truth. `ReasoningCase` is durable, and the deterministic critic produces structural diagnostics; it is **not** a semantic truth or independent vulnerability verifier.

One Research Specialist is integrated through the same MissionRuntime, router, Owner authority, and tool scopes. It does not create a parallel authority/runtime path. `scoped_http_probe` is a bounded, scope-authorized HTTP **GET** capability: redirects are blocked, credentials are not sent, and response bodies are not returned; the tool reports bounded metadata and a SHA-256 digest. This final verification did not contact a live target. General-web search remains unavailable/not implemented; GitHub repository search, where configured, is a separate capability.

The supervised SQLite queue atomically limits active entries to 10 by default and rejects overflow as `mission_queue_full` (HTTP 429). The worker processes one mission slice at a time, renews its lease during blocking model/tool calls, recovers expired leases, and preserves ambiguous in-flight effects for Owner reconciliation rather than replaying them blindly. `PlanStep` prerequisites are validated for duplicate IDs, missing steps, and cycles; execution waits for ready predecessors. Non-empty top-level `Plan.dependencies` and cross-mission dependency scheduling are not supported.

The persistent scheduler supports **one-time dispatch only** and rejects recurring `interval_seconds` and nonzero scheduled `retry_limit`; it does not create fresh recurrence executions or retry failed schedule dispatches. The current one-shot implementation is **not verified safe for timestamp ordering or dispatch handoff**: `run_at` is stored as an unchecked string, due selection compares SQLite text values lexically rather than normalized instants, and offset timestamps can therefore be ordered incorrectly. Dispatch enqueues into the queue database and only afterward marks the schedule complete in a separate scheduler-database update. A crash between those writes leaves the schedule eligible for redispatch; replay can reset an existing non-executing queue item and its attempt count because `enqueue` upserts it. The current tests cover one UTC one-shot dispatch and rejection of recurrence/retry settings, but do not cover offset/invalid timestamp inputs, reopening after restart, or an injected failure in the dispatch handoff. Timestamp normalization, handoff idempotency, and restart/crash behavior remain unverified; **do not describe dispatch as crash-safe**. This restriction is about scheduled jobs and does not erase separately bounded mission-recovery behavior. No recurring scheduling or cross-mission dependency work is in scope absent a new requirement.

## Owner-approved rules and remaining security gates

Use **two Owner-authorized test accounts and synthetic data by default**. Real data requires explicit scope and authorization. LLMs explain only; a deterministic, evidence-based verifier must decide whether a vulnerability is established.

A complete replayable request/response evidence chain remains required: each message/exchange must record method, URL, headers, request body, status, response headers and body, timestamps, synthetic/test-account identity, and request ID, with SHA-256 digests per message/exchange. It must never record secret values; secret-bearing values are represented only by `secret_ref` identifiers. Actual credentials, cookies, and tokens must remain in a separate encrypted, access-controlled Vault and be retained until the Owner manually deletes them.

### Owner-approved Vault architecture and execution requirements — NOT IMPLEMENTED

The required architecture has a **Computer Vault** and a **Phone Vault**. Local encrypted copies and keys use the computer's OS keychain and Android Keystore, respectively; secret data is encrypted locally and encrypted-synced between devices. A new device becomes trusted only after successful Owner username/password login, after which Owner login automatically restores Vault secrets. Device trust and login do **not** authorize every external target: secrets and tasks remain within the currently explicit Owner + Tool delegation and scope.

The root/recovery mechanism must support automatic recovery after login. A deployable key backend/manager is not implemented or configured; the specific key-provider backend remains unselected and **NOT VERIFIED**. The accepted design tradeoff is service-side recoverability. This requirement is not evidence of production-grade encryption, a configured provider, or a deployed key-management system.

At replay time, only after Owner, tool, and scope authorization, a worker secret resolver must decrypt the referenced secret on demand in mission Worker/Sandbox memory and pass it directly to the isolated HTTP client. Erasure after the step is best-effort. Secret values must never enter logs, stdout, databases, Evidence Chain, or Mission history. The required evidence remains replayable through its recorded request/response data and `secret_ref` identifiers, without copying secret values into the evidence.

These are Owner-approved acceptance requirements, **not implemented today**. The current repository has no Computer Vault, Phone Vault, cross-device sync, worker secret resolver, or authenticated two-synthetic-account BOLA/IDOR test flow. They do not relax non-bypassable authentication, authorization, scope, platform, or system safeguards.

The following critical items are **not implemented**: a full manual program-authorization capture/approval record bound to the Owner session and scope; the Computer/Phone Vaults, cross-device sync, automatic login recovery, deployable key backend/manager, worker secret resolver, and `secret_ref` access grants; an authenticated two-synthetic-account BOLA/IDOR test flow; the complete replayable HTTP evidence chain with secret values excluded; a deterministic independent vulnerability verifier; persisted `Finding`; a review-ready report; and an explicit Owner-approval workflow before disclosure. There is currently **no disclosure path**. Scope validation and the bounded probe do not substitute for these gates.
