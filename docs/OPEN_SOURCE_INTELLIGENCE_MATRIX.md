# Open-Source Intelligence Matrix

**Scope.** This matrix records implementation ideas that can be adapted into CyberSentinel X without importing an external runtime or model weight. The entries distinguish observed upstream capabilities from CyberSentinel recommendations. License statements are intentionally conservative: a model family is not a license for every checkpoint, and the exact model card must be verified before redistribution or deployment.

| Project / family | Observed capability | Relevant implementation pattern | CyberSentinel adaptation | Security / license caveat | Primary source |
|---|---|---|---|---|---|
| Qwen3 | Public documentation describes thinking and instruct variants, tool usage, long-context operation, OpenAI-compatible serving, and Qwen-Agent/MCP integration. | Preserve reasoning content and treat it as a model trace, while representing tool calls separately from assistant text. | Use the existing provider-neutral `ModelTurn`, `ToolCallProposal`, and `ReasoningContinuation`; never treat reasoning text as authority. | Qwen3 README states its open-weight models are Apache 2.0; verify the exact checkpoint and serving stack. | [Qwen3 repository](https://github.com/QwenLM/Qwen3) |
| DeepSeek | Open-weight reasoning models are commonly served through OpenAI-compatible APIs and expose reasoning/tool-use integration through ecosystem adapters. | Separate reasoning-channel preservation from tool-call parsing and continuation. | Populate `ReasoningBudget` and keep provider capability flags truthful rather than inferring tool support from model name. | Check the exact DeepSeek model card and commercial terms; do not assume family-wide licensing. | [DeepSeek organization](https://github.com/deepseek-ai) |
| Llama | Llama-family checkpoints are widely integrated with chat templates, structured outputs, and tool-use serving layers. | Treat the tokenizer/chat template as a protocol adapter, not as the authority boundary. | Keep `ConversationTurn` provider-neutral and convert at the provider edge; validate tool-call IDs before execution. | Meta Llama licenses and acceptable-use terms are checkpoint-specific and are not equivalent to Apache/MIT. | [Meta Llama repository](https://github.com/meta-llama) |
| Mistral | Mistral publishes open and commercial model variants with function-calling support in several deployment paths. | Capability negotiation must be explicit: native chat, structured output, parallel tools, reasoning, and vision are independent flags. | Extend `ProviderCapabilities` and reject unsupported native features honestly. | License varies by model and release; verify the model card and terms before use. | [Mistral AI repositories](https://github.com/mistralai) |
| GLM | GLM-family projects provide open-weight checkpoints and serving/inference guidance; tool support depends on the selected release and adapter. | Keep model-family knowledge separate from provider capabilities and runtime authorization. | Use the same `RouterModelIntelligence` adapter only when the provider advertises native tool calling. | Verify the exact GLM checkpoint license and whether its reasoning/tool fields survive the serving proxy. | [THUDM repositories](https://github.com/THUDM) |
| Gemma | Google publishes Gemma model cards and ecosystem integrations, including tool-use-capable serving paths for selected releases. | Use a strict model-card allowlist for model, context length, and supported message format. | Add provider/model capability snapshots to mission provenance; fail closed on unsupported tool formats. | Gemma uses Google-specific terms; it is not automatically interchangeable with Apache-licensed weights. | [Google Gemma repository](https://github.com/google-deepmind/gemma) |
| Hugging Face Transformers | Official docs define passing JSON schemas/functions to chat templates, assistant `tool_calls`, and subsequent `tool` messages; multiple calls require IDs and disambiguation. | Tool requests are proposals; the host executes them and appends stringified results. | `ContextAssembler` emits explicit tool-role continuations and `execute_bounded_parallel` preserves call identity/order. | The docs explicitly warn that code/tool execution needs host-side safety; model/parser support varies. | [Transformers tool-use docs](https://huggingface.co/docs/transformers/main/en/chat_extras) |
| LangGraph | The official repository emphasizes durable execution, resumption, human-in-the-loop, short/long-term memory, and traceable state transitions for long-running agents. | Durable state is the source of truth; resume from checkpoints rather than replaying ambiguous side effects. | Reuse the pattern through `Mission.checkpoint`, `ContextAssembler`, recovery-required status, and provenance events without adding LangGraph. | External orchestration would add a dependency and policy surface; adapt the state ideas only. | [LangGraph repository](https://github.com/langchain-ai/langgraph) |
| AutoGen | AutoGen exposes layered event-driven multi-agent/runtime APIs, AgentChat abstractions, extensions, MCP workbenches, and tool iterations. The upstream README now marks AutoGen maintenance mode. | Separate transport/runtime, agent policy, tool workbench, and application authorization. | Do not add AutoGen; use its layered boundary as a design comparison for provider adapters and tool work. | Maintenance mode and trusted-MCP warning make dependency adoption unattractive for the core security boundary. | [AutoGen repository](https://github.com/microsoft/autogen) |
| OpenHands | OpenHands provides agent-server/workspace abstractions, multiple backends, automations, scheduled/event-triggered execution, and explicit warnings about filesystem access. | Treat workspace/server boundaries as privileged resources and make automation provenance explicit. | Extend current scope snapshots and authorization checks for future remote workspaces; keep all side effects behind tools. | The official README warns that agent-server access can expose the filesystem; isolation and hardening are mandatory. | [OpenHands repository](https://github.com/All-Hands-AI/OpenHands) |
| SWE-agent | SWE-agent exposes a configurable tool-using agent for repository tasks and emphasizes simple, hackable research trajectories; the README recommends mini-SWE-agent for new work. | Record trajectory, tool action, observation, and verification separately so evaluations are replayable. | Use `TrajectoryEvent`, `MODEL_TURN`, durable action history, evidence, and deterministic verification. | Repository/code execution is high risk; use authorization, scope, sandboxing, and failure recovery rather than copying broad agency. | [SWE-agent repository](https://github.com/SWE-agent/SWE-agent) |
| smolagents | Hugging Face describes CodeAgent and ToolCallingAgent modes, model/provider agnosticism, MCP/tool integration, and sandbox options. It explicitly states LocalPythonExecutor is not a security boundary. | Keep code generation and execution separate; use a real sandbox for untrusted code. | Retain typed tool calls and authorization; never add arbitrary Python execution to the core registry. | Sandbox warning is directly applicable: no local executor or generated code may bypass CyberSentinel authorization. | [smolagents repository](https://github.com/huggingface/smolagents) |
| Model Context Protocol | The specification standardizes resources, prompts, tools, capability negotiation, progress, cancellation, and JSON-RPC stateful connections. It requires host-side consent and warns that tool descriptions/data are untrusted. | Protocol capability negotiation is distinct from authorization; tools/resources are untrusted until host policy validates them. | The existing registry/authorization path is the host boundary; future MCP adapters must map to the same `ToolCallProposal` and scope checks. | MCP does not enforce safety itself; consent, access control, privacy, and tool authorization remain host responsibilities. | [MCP specification](https://modelcontextprotocol.io/specification/2025-06-18) |

## Selection conclusions

The highest-value adaptations are **protocol separation**, **durable state reconstruction**, **trajectory-level observability**, **capability honesty**, and **sandbox-first execution**. No external framework is required to implement these ideas. Conversely, copying a code-agent executor, arbitrary filesystem access, or an MCP server without the current authorization boundary would weaken CyberSentinel X and is explicitly rejected.

## Attribution and reproducibility

The matrix was prepared from the official repositories and documentation linked in the final column. Upstream features and warnings should be rechecked at integration time because model cards, releases, license terms, and maintenance status change independently of CyberSentinel X releases.
