# هوية تشغيل وACL مستقلة: ليست تفعيلًا لخلفية العزل

## ما تضيفه هذه الشريحة

يضيف `workspace/windows_appcontainer_workspace.py` مساحة عمل جديدة وهوية AppContainer فريدة لكل تشغيل. الواجهة `WindowsAppContainerWorkspace.create(root)` تعيد `run_id` و`identity_name` و`sid_string` و`workspace_path`. تستخدمها جهة broker موثوقة فقط، لا agent ولا مشروع غير موثوق. لا تطلق الواجهة أي عملية ولا تتصل بـMissionRuntime أو تغيّر `PROCESS_SANDBOX_UNAVAILABLE / RESOURCE_BLOCKED`.

تُشتق SID أصلية من اسم عشوائي داخلي عبر [DeriveAppContainerSidFromAppContainerName](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deriveappcontainersidfromappcontainername). لا يُنشأ ملف تعريف AppContainer: [CreateAppContainerProfile](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile) يضيف مجلدات وتخزين registry خارج مساحة العمل، وهو غير مناسب لادعاء حصر كل الكتابات هنا. الهوية المشتقة ليست حساب مستخدم مسجلًا، وتحرير ذاكرة SID لا يبطل token صدرت سابقًا.

توثيق Microsoft يصف الاشتقاق بأنه إحضار SID لاسم ملف تعريف، ويعرض إنشاء ملف التعريف في مسار الإطلاق المعتاد؛ لا يعطي ضمانًا صريحًا لدعم الإطلاق دون ملف تعريف أو غياب تخزين ضمني على كل نظام. لذلك هذا **مسار تجريبي مستقل يحتاج إثباتًا أصليًا**، لا وعد دعم إنتاجي. يجب أن يفشل الاختبار إن لم تعمل الهوية المشتقة أو ظهر ملف تعريف ضمني، دون الرجوع بصمت إلى إنشاء profile.

## حقوق المساحة وفصل التحكم

يلزم root محلي NTFS موجود مسبقًا، لا reparse point، وتحت سيطرة broker. لا يجوز السماح لمشروع أو هوية تشغيل باستبداله أو تعديل أسلافه. تُنشأ مساحة جديدة بواصف أمني صريح منذ الإنشاء؛ DACL محمية بدل استيراد أذونات واسعة من الأب. التحكم يبقى لـSYSTEM وهوية broker، بينما لا تُمنح SID التشغيل إلا حقوق بيانات المساحة والتنقل اللازمة، لا إدارة ACL أو تغيير المالك. لا منح لـ`ALL APPLICATION PACKAGES` أو capabilities أو صلاحيات على جذر المستخدم أو القرص.

تُضبط ملكية مجلد التشغيل صراحةً إلى SID مستخدم broker بدل الاعتماد على مالك token الافتراضي. تمنع ACE محدودة لـ`OWNER RIGHTS` استعادة المالك لحق `WRITE_DAC` الضمني، وتبقى موجودة عند سحب الإذن أيضًا؛ لا يحجب ذلك التحكم الصريح الممنوح لـbroker وSYSTEM. يشمل رفض الأذونات الواسعة مجموعتي `ALL APPLICATION PACKAGES` و`ALL RESTRICTED APPLICATION PACKAGES`. تتضمن حقوق البيانات `READ_CONTROL` اللازم لفتح الملفات بعمليات `GENERIC_READ/WRITE`، دون `WRITE_DAC` أو `WRITE_OWNER`، ودون منح تنفيذ للملفات الناتجة.

تحتاج عملية LPAC منخفضة النزاهة إلى mandatory integrity label ملائمة داخل المساحة؛ هذه لا تستبدل فحص DACL. يجب أن تكون اختبارات الرفض خارج المساحة منخفضة النزاهة أيضًا حتى لا تنجح بالاعتماد على MIC وحده بدل عزل الهوية.

يميز فحص الأسلاف بين [إنشاء عنصر جديد وحذف عنصر قائم](https://learn.microsoft.com/en-us/windows/win32/fileio/file-access-rights-constants): قد تسمح ACL نظامية لمستخدم عادي بإنشاء مجلد مجاور على سلف أعلى؛ ذلك وحده لا يمنحه استبدال السلسلة الموجودة أو الكتابة داخل root المحمية. تُرفض على الأسلاف حقوق الحذف وتعديل ACL والمالك والخصائص وEA و`GENERIC_WRITE` الواسعة. وبالنسبة إلى مجموعتي الحزم العامتين تُرفض حقوق الإنشاء أيضًا، لأنها تمنح كتابة خارجية معروفة للحاويات. لا يفحص هذا جميع ACLs الجهاز أو المجموعات المخصصة؛ تبقى مسؤولية الجهة الموثوقة التأكد من سيطرتها على السلسلة وعدم تمكين جهة غير موثوقة من استبدالها.

## ما يجب أن تثبته Windows فعليًا

يوجد probe ثابت موثوق للاختبار فقط، وليس process launcher منتجًا. يستخدم `SECURITY_CAPABILITIES` مع SID التشغيل وبدون capabilities، ويضيف `PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT` كما في [عقد إطلاق LPAC الرسمي](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer). تُفحص token الفعلية قبل استئناف العملية، ثم من داخل العملية؛ لا يكفي تمرير flags أو `cwd`.

الاختبارات تتطلب قراءة وكتابة وإنشاء فعليًا داخل المساحة، و`ERROR_ACCESS_DENIED` عند محاولة الكتابة والإنشاء في أهداف خارجية موجودة يسمح بها broker، وعند الوصول إلى مساحة تشغيل آخر. لا تعتبر `PATH_NOT_FOUND` إثباتًا لمنع ACL. تتطلب أيضًا خروج العملية وانتهاء handles قبل التنظيف، وسحب إذن SID ثم حذف الموارد المملوكة فقط. غياب LPAC أو compiler أو أي قدرة أصلية مطلوبة على Windows فشل، وليس skip.

تحفظ بوابة `native-appcontainer-workspace` دليل JUnit وJSON على SHA نفسه، وترفض غياب أي اختبار أصلي أو skip أو failure. لا يُعد نجاح الاختبارات المحمولة على Linux إثباتًا لـWindows، ولا يُعد نجاح هذه البوابة قبولًا لمهمة كاملة.

## القراءة خارج المساحة: الاستثناءات وحدود allowlist

تحتاج fixture إلى قراءة/تنفيذ ملف probe واحد، يُمنح صراحةً لـSID المحددة داخل دليل تحكم موثوق، لا لأي حزمة أخرى. يُبنى probe بـCRT ساكنة لتقليل تبعيات runtime، ولا تُمنح حزمة Python أو مجلدات المستخدم صلاحيات واسعة. تبقى قراءة DLLs الأساسية لـWindows وبيانات النظام التي تسمح بها سياسات LPAC القائمة على الجهاز جزءًا من تشغيل Windows نفسه؛ هذه الشريحة لا تعدل ACLs النظام ولا تدّعي أن ذلك محصور في قائمة مسارات تحقق منها broker.

توضح [عزلة AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) أن الوصول يتحدد بالهوية والموارد الممنوحة. LPAC تقلل الوصول العام مقارنةً بـAppContainer العادية، لكنها ليست مرشح ملفات قائمًا على قائمة مسارات. **منع كل كتابة خارج المساحة والسماح بالقراءة فقط من runtime allowlist صريحة لا يزال شرط قبول غير مثبت على مستوى الجهاز أو backend المنتج.** نجاح أهداف الرفض المحددة لا يثبت غياب كل مجلد أو خدمة أو جهاز آخر قد يسمح به نظام آخر. يلزم قبل التفعيل اختبار المسارات الفعلية لـOS/runtime/temp/profile/registry والأجهزة وروابط reparse وواجهات broker، ثم جمع الطبقات مع VHD وJob والشبكة وحدود الموارد والفنس وإيصالات البدء.

## التنظيف ليس إبطالًا سحريًا للهوية

يستدعي broker `close()` فقط بعد التأكد من انتهاء جميع العمليات التي استخدمت الهوية وإغلاق handles. سحب DACL لا يسحب حقوق handle مفتوحة مسبقًا، وتحرير SID لا يمنع أحدًا من اشتقاق البتات نفسها مجددًا؛ الحماية من إعادة الاستخدام هي اسم عشوائي غير مكرر وإزالة الأذونات والموارد. أي فشل تنظيف ظاهر وقابل للمحاولة، ولا يجوز إخفاؤه أو اعتباره قبولًا. التعافي من crash للـbroker وتعداد موارد التشغيل ليستا ضمن الشريحة.

يختبر harness فشل الحذف المحقون بعد سحب ACL الأصلي، مع الاحتفاظ بملف أنشأته LPAC فعلًا وإعادة تشغيل SID القديمة لفحص رفض القراءة والكتابة وفتح `WRITE_DAC/WRITE_OWNER`. يمنح الاختبار اجتيازًا فقط لمجلد الملف حتى لا يخفي منعُ اجتياز الأب خللًا في DACL الملف؛ تبقى حقوق الملف مسحوبة. ثم يعيد broker محاولة التنظيف. تغطي الاختبارات المحمولة `KeyboardInterrupt/SystemExit` أثناء التهيئة، والمحافظة على إشارة الإلغاء مع تنظيف الموارد أو إرفاق كائن تعافٍ قابل للمحاولة عند الفشل؛ لا تُمس مساحة موجودة سلفًا عند تصادم الاسم.

تظل تطبيقات VHD وJob السابقة دون تعديل. لا تغيير لـmain أو tags/releases أو Cloudflare.
