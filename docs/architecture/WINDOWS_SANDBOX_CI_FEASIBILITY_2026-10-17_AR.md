# عزل Windows: ما يستطيع CI إثباته وما يزال يمنع التفعيل

## القرار

يبقى backend Windows معطّلًا، وتبقى `RESOURCE_BLOCKED` عند `run_project_tests` نتيجة صحيحة وليست نجاحًا. لا يُضاف إطلاق جزئي أو `Popen` بصلاحيات المضيف. يبدأ هذا العمل من `328d9d491b4f556f75abb4e31d531fe772929db5` على فرع المراجعة، وهو ابن `a6204fb` بتقييم API توثيقي فقط.

**CI الأصلي موجود ويمكن استخدامه.** عدم وجود Windows في مساحة العمل المحلية ليس دليلًا على تعذر التنفيذ. لكن وجود runner لا يعني وجود backend مكتمل أو تحقق حدوده. التركيب المقترح ممكن من حيث واجهات النظام، ولم يُثبت تكامله الأمني في المنتج؛ لا توجد نتيجة تبرر تمكينه الآن.

## ما ثبت بالفعل

في [تشغيل Windows السابق على 328d9d4](https://github.com/mosfiry/cybersentinel/actions/runs/39030930830)، جرى بناء المثبت وتشغيل التطبيق والاستدلال المحلي؛ ظل قبول Mission الكامل FAIL بسبب غياب sandbox. أدلة المثبت تربط `source_commit` بالـSHA نفسه. دورة الاستعادة المسجلة للمهمة المحجوبة تحمل `restart_basis=VERIFIED` وإعادة تحقق Owner، مع `dispatch_attempted=false` و`process_started=false`. هذه أدلة استمرارية للحجب، لا أدلة تنفيذ اختبارات المشروع.

الشيفرة في `workspace/process_sandbox.py` ترفض Windows قبل callback الإطلاق. أما `scripts/windows_process_job.py` فتملك Job لتشغيل التطبيق/المثبت وتنظيف شجرته، وليست backend لعزل المشروع. الاختبارات الأصلية الثلاثة في `tests/test_windows_process_job.py` لم تكن ضمن قائمة اختبارات Windows المحمولة في workflow المثبت؛ تُضاف بوابة مستقلة لتشغيلها مباشرة مع اختبارات الحجب، دون انتظار Qwen أو اعتبار نجاحها قبولًا للعزل.

## حدود runner ليست حدودًا للعملية

يستخدم المستودع `windows-latest`. توثق [GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#administrative-privileges) أن Windows hosted runners تعمل كمسؤول مع تعطيل UAC. هذه صلاحية كافية لاستكشاف إعدادات النظام في اختبارات مستقلة، لكنها ليست إثباتًا لتوفر Hyper-V أو وسيلة quota بعينها، ولا إثباتًا لعمل منتج مثبت بصلاحيات مستخدم عادي. يجب حفظ هوية image وإصدار النظام مع نتائج SHA لأن تسمية `latest` متحركة.

لا تُعد مساحة القرص أو ذاكرة VM أو مهلة job في Actions حدًا أمنيًا لكل Mission. يجب أن يفرض backend حدوده قبل أول تعليمة مشروع غير موثوقة، داخل runner وخارجه. ولا يجوز تشغيل pytest المملوك للمشروع بصلاحيات الإدارة التي يوفرها CI كبديل للعزل.

## الفجوات التنفيذية المحددة

| المطلوب | الآلية المرشحة | ما ينقص قبل الإثبات |
|---|---|---|
| هوية OS معزولة | AppContainer/LPAC مع capabilities ضيقة | إنشاء token/SID والتحقق منهما وإطلاق Python فعلي؛ لا يوجد ذلك في backend الحالي. |
| ملفات محصورة | مدخل مشروع منقّى للقراءة فقط وACL على runtime ومسارات إخراج محددة | منع ملفات المستخدم وDB وأسرار التطبيق، والتحقق من reparse/traversal وتبديل المسارات؛ لا يكفي cwd. |
| شبكة default-deny | AppContainer بلا capabilities شبكة، دون استثناء loopback | اختبارات منع من داخل العملية مع positive-control من المضيف حتى لا يبدو غياب خادم الاختبار كمنع أمني؛ IPv4/IPv6 وDNS والمنافذ الواردة. لا تعدّل firewall العام للـrunner. |
| ذاكرة وعدد عمليات إجماليان | `JobMemoryLimit` و`ActiveProcessLimit` | ضبط الحدود والتحقق منها قبل Resume، وتجاوز مجموع أبناء متعددين لا عملية منفردة فقط. حد الذاكرة هنا committed memory. |
| CPU وزمن حقيقي | Job CPU accounting/rate مع supervisor monotonic خارجي | تمييز CPU rate عن ميزانية CPU التراكمية، ومهلة walltime؛ إثبات الإنهاء والسبب وتنظيف الأبناء عند انهيار worker. |
| حد قرص/كتابة إجمالي | مساحة OS مستقلة محدودة أو quota مثبتة | لا يقدم Job حصة قرص. حدود artifact في Python لا تمنع الكتابة المباشرة. لا توجد آلية منفذة أو اختبارات امتلاء مشتركة للأبناء. |
| ملكية الإطلاق والإلغاء | Job مستقلة، launch-bound أو suspended/assign/verify/resume، handles مملوكة | ربطها بأداة Mission وفنسها وإلغاء Owner ومنع breakaway والتحقق من Job متداخلة في CI، لا إعادة استخدام harness باعتباره sandbox. |
| دليل بدء دائم | receipt OS مربوط بـMission/request/action/tool-call وسجل effect | حفظ الدليل بعد تحقق الهوية/Job وقبل قبول نتيجة الأداة؛ crash بعد بدء محتمل يظل ملتبسًا ولا يعاد تلقائيًا. |

تصف [Microsoft حصص NTFS](https://learn.microsoft.com/en-us/windows/win32/fileio/managing-disk-quotas) بأنها لكل **مستخدم على volume**، مع اختيار منع مزيد من التخصيص عند تجاوز الحد؛ هذا لا يثبت حصة مستقلة لكل AppContainer/Job تحت مستخدم واحد. يلزم قرار معماري واختبار، لا افتراض أن SID الحاوية يغير تلقائيًا حساب quota. قرص VHD محدود الحجم مرشح منفصل، وليس حلًا مثبتًا: يجب حصر **كل** مسارات الكتابة، بما فيها temp/profile الافتراضي ومسارات الأبناء، عليه، وضبط ACL ومنع مسارات هروب، والتحقق من الامتلاء والتنظيف والأعطال. يحتاج إعداد القرص وملكيته وتركيبه إلى تصميم امتيازات للمنتج المثبت؛ صلاحيات CI الإدارية وحدها لا تحل ذلك.

[تقييم واجهات النظام الموجود](WINDOWS_SANDBOX_NATIVE_API_EVALUATION_2026-10-17.md) يشرح لماذا لا تكفي `Experimental_CreateProcessInSandbox`: قيود inherited handles وغياب configurable resource bounds وتكامل Job المطلوبة. لم يتغير هذا القرار.

## شرائح تالية محدودة وبوابات إيقاف

تقتصر الشريحة الحالية على CI واختبارات الحجب وJob lifecycle وتقرير الجدوى؛ لا تعدّل مسار التنفيذ الإنتاجي أو Owner أو Scope أو allowlists أو cancellation. نجاح بوابة الحجب يعني سلامة الرفض فقط. تبقى اختبارات منع الملفات والشبكة والموارد والإطلاق الفعلي **غير مثبتة**، ولا تُنشأ لها اختبارات نجاح صورية أو Evidence مصطنعة.

تبدأ الخطوة التالية بإثبات مستقل للتخزين المحدود على Windows: مساحة صغيرة محدودة فعلًا، ومحاولة كتابة مباشرة من أبناء متعددين وملف profile، مع positive control وفحص cleanup وفشل الإعداد. إن تعذر حصر كل الكتابة، يتوقف مسار AppContainer المقترح ويُقيّم عزل مكافئ؛ لا يُفعّل backend.

بعدها شرائح منفصلة لهوية AppContainer/LPAC وACL ومنع الشبكة، ثم حدود Job وsupervisor مع حالات crash/cancel/breakaway، ثم دمج receipt والفنس والـledger. لا يُوصل ذلك بـ`run_project_tests` المتاح إلا بعد اجتياز اختبارات OS السلبية والإجمالية واختبار Mission محكومة فعليًا بأدلة دائمة. أي غياب capability أو فشل إعداد يعيد الحجب قبل dispatch؛ وأي بدء ملتبس يطلب recovery، لا نجاحًا ولا replay.

## قرار الدمج

تُراجع التغييرات وتُختبر وتُدفع فقط إلى فرع المراجعة. يُفحص CI وartifacts على SHA النهائي؛ لا يُدمج فرع ما دام القبول المطلوب FAIL، حتى لو اجتازت بوابة الرفض المستقلة. لا تعديل لـ`main` أو tags/releases أو Cloudflare، ولا استدلال مدفوع أو سحابي.
