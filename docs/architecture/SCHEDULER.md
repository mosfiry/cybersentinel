# Mission and Task Scheduling

The canonical execution path remains `MissionStore`, `MissionQueue`, the worker, and `MissionRuntime`. It persists leases/checkpoints, revalidates Owner authorization, fences effects, and quarantines ambiguous in-flight work rather than replaying it automatically.

`AgentCore` opts new and resumed missions into a deterministic `MissionTaskGraphAdapter`. It maps existing plan steps into a dependency graph and gates dispatch on a current, authorized ready node. Graph state is embedded in the integrity-covered Mission payload; claim/completion updates are persisted with Mission checkpoints and action history. The adapter runs one coordinator task at a time by default. It does not create independent workers or a second MissionQueue. See [Mission-Atomic Task-Graph Dispatch](MISSION_TASK_GRAPH_DISPATCH.md).

## Background execution and recovery

In Desktop mode, the loopback Bridge constructs the durable `MissionQueue`, `MissionScheduler`, `MissionWorker`, and `RuntimeSupervisor` and starts a non-daemon worker thread. Startup performs expired-lease recovery before the first queue poll. The renderer window can be closed to the system tray while the Bridge and worker stay alive; an explicit Quit action shuts down the Bridge and drains the active synchronous worker call. On the next app start, persisted Missions and schedules are recovered from SQLite. The standalone `python -m scripts.run_mission_worker` entrypoint also supports supervised headless execution without a Desktop renderer.

Closing the window is not the same as installing an always-on OS service. If the Desktop app is explicitly quit or the host shuts down, no worker runs until the application or standalone process is launched again. No automatic OS boot registration, multi-host high availability, or coordinated backup across the mission databases is established.

## Schedule limits

The production scheduler currently supports Owner-authorized one-shot and delayed dispatch, durable schedule/queue handoff, cancellation through the Owner Mission-cancel action, and fail-closed restart recovery. `POST /api/public/missions/{mission_id}/schedule` is Owner-cookie and CSRF protected and accepts exactly `{ "run_at": "<timestamp>" }`; recurrence, cron, retry, client-supplied schedule identity, and unknown fields are rejected before reaching the service. New schedule creation pins the exact integrity-covered Mission and non-empty ScopeSnapshot digests; dispatch rechecks those plus the immutable authorization snapshot.

Recurring schedules, cron expressions, and per-occurrence Mission creation are not enabled. The current authorization snapshot is bound to one Mission ID, Owner approval, session, scope, and expiry; the system has no separately Owner-approved reusable schedule grant capable of minting unique occurrence identities while preserving—not silently renewing or broadening—that exact authority. At expiry or any authorization/scope/integrity drift, dispatch quarantines the schedule and requires Owner reauthorization. Automatic Mission retry is not enabled: after queue dispatch, provider/tool completion may be ambiguous, and the system has no safe proof of zero effect for arbitrary Missions. Transaction rollback before queue promotion is the only automatic reattemptable boundary. Ambiguous provider/tool outcomes remain quarantined for Owner reconciliation. There is no schedule-management UI or list/update/delete API, and Windows acceptance remains open.
