# Provider System

The model side uses provider-neutral request/response types and the `ModelRouter`/OpenAI-compatible adapter. The local model manager provides guarded model lifecycle and supply-chain checks for its supported llama.cpp path. These are reusable foundations; new provider implementations should satisfy the same provider contract rather than branch AgentCore execution behavior.

## Provider metadata and routing

`ProviderMetadata` is a validated, immutable projection of provider ID, model identity/version, quantization, context length, capabilities, deployment locality, and structured hardware requirements. `OpenAICompatibleProvider.status()` exposes this metadata without the API key. The local llama.cpp runtime binds metadata from its validated `ModelSpec` (including Qwen3 and DeepSeek catalog entries); generic endpoints accept bounded explicit metadata through `*_LLM_*` settings. Capability flags and locality for generic endpoints remain configuration assertions, not remote attestation or automatic model capability discovery. Hardware requirements describe the deployment; they do not detect actual hardware.

Deployment is `local`, `remote`, or `unknown`. Unknown is the default for generic providers and is fail-closed for fallback: absent an explicit deployment class, only the highest-priority configured provider is eligible. By default, normal generation and tool-calling may fail over only among providers with the same deployment class as the primary provider. A local-to-remote or other cross-deployment fallback requires `LLM_ALLOW_CROSS_DEPLOYMENT_FALLBACK=true`; that opt-in is strict, and `ModelRouter.last_trace` records the cross-deployment transition. Blocked providers are also recorded in the trace. `generate_for_provider` remains exact provider/model bound and never falls back. The context window is computed only from providers reachable under this policy; an unknown window on any reachable provider disables the shared token ceiling.

OpenAI-compatible servers can serve supported Qwen, DeepSeek, or future model families without AgentCore changes when their API and configured capabilities conform. The current local catalog/runtime supports its pinned llama.cpp CPU path. Native vendor-specific APIs, H3-specific integration, live capability discovery, GPU/backend selection, and real end-to-end model inference remain unverified; provider metadata or catalog presence is not acceptance evidence. Locality labels are operator assertions and cannot prove that a proxy/tunnel does not forward requests elsewhere.

## Search providers

The search side uses `SearchProvider`, `SearchRequest`, `SearchResponse`, and `SearchService`. Local knowledge and the GitHub, NVD, and MITRE providers remain separate scopes. The `web` scope has a read-only DuckDuckGo HTML adapter that uses `security.pinned_http.PinnedSession`, refuses redirects, bounds response bytes and results, hashes provenance, and labels returned material untrusted. Search integration routes through the canonical `search` ToolSpec, whose risk metadata identifies network-read access.

The web adapter reports `IMPLEMENTED`; it does not claim that a third-party endpoint is reachable. In this environment the live DuckDuckGo probe returned HTTP 202 with an anti-automation page and no result markup, so the provider correctly reports a typed unavailable error for that response. Real live search acceptance is therefore blocked by the endpoint response, not inferred from mocked tests. The dated endpoint, method, observation, and scope are recorded in [`PROVIDER_LIVE_CHECK.md`](PROVIDER_LIVE_CHECK.md).
