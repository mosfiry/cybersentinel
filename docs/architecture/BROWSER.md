# Browser Automation

CyberSentinel now provides a bounded in-process Browser subsystem backed by the exact Playwright version pinned in `requirements-runtime.txt` and its corresponding Chromium build. The canonical `browser` ToolSpec exposes open/navigation, text extraction, link discovery, safe DOM/structured inspection, screenshots, inert file downloads, and session close; `browser.fill` is a separate state-write ToolSpec. This is a real Chromium runtime, not a search-provider wrapper or an empty abstraction. Search result URLs remain metadata only unless an independently authorized Mission explicitly invokes Browser.

Every Browser action uses the canonical flow **Agent proposal → current Owner/Mission authorization and Scope Firewall check → registered Browser ToolSpec → bounded Chromium action → fenced evidence/artifact receipt**. The Browser ToolRegistry injects a non-serializable ExecutionContext only after revalidating canonical Owner identity/session, Mission integrity/authorization, scope snapshot, signed tool decision, active execution fence, and strict Mission evidence store. Browsing and authorization remain separate: page text, links, scripts, form labels, screenshots, and downloads are untrusted observations and cannot grant permissions or alter Owner policy.

Browser requests are intercepted and re-fetched through the existing DNS-pinned HTTP transport; Chromium itself uses a fail-closed dead proxy, so browser networking cannot bypass per-request Scope Firewall checks. Playwright's Chromium OS sandbox is explicitly enabled, and POSIX root execution is rejected rather than disabling the sandbox. Redirect destinations are checked before Chromium receives the redirect and again on the resulting request. Only GET/HEAD are allowed; WebSockets, service workers, local files, cleartext public HTTP, private/link-local addresses, credential headers, and out-of-scope targets are denied. Browser sessions are in-memory, isolated, TTL/count/byte bounded, and bound to exact Owner+session+Mission+scope/target identities. Content is scrubbed and labelled untrusted; no prompts, credentials, Owner instructions, or authorization objects enter the page context.

Form fill is separately classified `state-write`, limited to non-sensitive text/search/URL/number fields, and always disables network, never submits, hashes rather than persists the value, and closes the session. Downloads have byte limits, reject active/archive suffixes, are never opened/executed, and are persisted only as opaque UNVALIDATED Mission artifacts with content/manifest hashes and fenced provenance. Screenshots, extraction, links, and DOM inspection create the same class of opaque untrusted artifacts and append bounded evidence records. Registry and Browser operation timeouts/cancellation fail closed.

The existing desktop application's hardened renderer/preload boundary remains separate from Browser automation. Linux/Docker and Windows build workflows install the pinned Chromium runtime; the Windows backend packaging script copies the matching browser store into Electron resources and has a real bundled-runtime smoke test. The local Linux smoke launched Chromium from the copied Electron resource layout with its OS sandbox enabled. Automated local/CI integration is not equivalent to Windows user acceptance, live public-target acceptance, or a signed/released installer. Browser has no separate interactive-window UI, no credential autofill, no cross-mission cookies, no secret-bearing form writes, and no automatic retrieval/rendering of stored artifacts. Real local Chromium tests do not claim live Qwen, broad website, or end-user deployment acceptance.
