# Blocker D: preflight persistence and restart reconciliation

## Verdict

The available evidence does **not** prove a MissionStore persistence or recovery defect for the Windows AppContainer preflight rejection. It distinguishes three Mission states and prevents them from being conflated:

1. In the earlier Windows run `39002439803`, the installed-desktop fixture was paused immediately after Mission creation, before the worker began execution. It therefore had no tool proposal, preflight attempt, or failure record to persist.
2. A separate source-tree full-E2E Mission in that run did reach `run_project_tests`; its AppContainer preflight rejection was truthfully recorded as `RESOURCE_BLOCKED`, `not_dispatched`, and `process_started=false`.
3. In Windows CI run `39009257440` on SHA `37aa3baf83aed7c9bb780bb084b80aa110a161b9`, the installed-app Mission did persist that same kind of preflight failure. The final gate rejected its restart basis because the validator required an external `ScopeSnapshot` ID that the public local-project flow does not create. The record was present; the acceptance-harness binding check was wrong for that supported scope representation.

No evidence supports synthetic process-start, tool-result, evidence, or success events. The overall project-test acceptance verdict remains **FAIL** until the Windows sandbox backend actually executes the bounded test and independently verifies its evidence/result. A verified preflight record is only a restart/reconciliation basis, never Mission success.

The report directory for run `39003631333` is not present on this computer; forensic comparisons here use the available `39002439803` artifacts and the Windows CI artifact for `39009257440`.

## Evidence and cause

### Earlier Mission that had no attempt

`/workspace/cyber-incident-evidence-39002439803/new/desktop-ui-acceptance.json` reports, before restart:

- `mission_status=READY`, `queue_state=paused`, `pause_requested=true`;
- exactly two timeline events (`MissionStarted`, `PlanCreated`);
- zero evidence records; and
- execution-chain status `NOT_PRESENT`.

After restart it reports `OWNER_REAUTH_REQUIRED` / `needs_input`, with the same two timeline events, zero evidence, and no execution chain. `scripts/windows_desktop_acceptance.py::_installed_app_mission` created the Mission and then posted `/pause` immediately; it did not wait for a worker claim, model turn, tool proposal, authorization decision, or preflight result. There was no actual attempt to save for this Mission. Its post-restart reauthentication/quarantine is correct and it was not auto-resumed.

### Durable preflight failures

The separate source-tree fixture in the available `39002439803` artifacts records AppContainer as unimplemented and the project-test tool call as rejected before process dispatch/start. Its Mission is `RESOURCE_BLOCKED` with `checkpoint.status=not_dispatched`, `dispatch_attempted=false`, `process_started=false`, and a bound `PROCESS_SANDBOX_UNAVAILABLE` failure diagnosis.

The later Windows CI artifact for `39009257440` independently reports:

- `mission_status=RESOURCE_BLOCKED`, `queue_state=failed`;
- `resource_checkpoint_diagnostics.status=not_dispatched` and `reason_code=backend_unavailable`;
- a `PROCESS_SANDBOX_UNAVAILABLE` failure for `run_project_tests`;
- zero evidence records, zero project-test result records, and zero successful result records;
- `authorization_binding_verified=true` and `scope_firewall_verified=true`; and
- `restart_basis.status=BLOCKED`, `kind=NOT_RUN`, `reason=mission_integrity_or_scope_binding_invalid`.

No application restart was completed in that run (`persistence_after_application_restart=false`), so its post-restart no-auto-resume/reauth behavior was **not** tested by that artifact. The failure was before the restart callback, not a missing MissionStore record.

### Root cause in the restart-basis validator

The public desktop path (`bridge.py::_public_scope_context`) stores its local-project authority in the Mission's `scope_snapshot` field as a project-bound context containing `target_id=local-project:<project_id>`, `workspace_root`, `scope=["workspace"]`, the Owner-request-derived `allowed_tools`, and empty network/credential allowlists. Its `authorization_context` intentionally has no separate external `ScopeSnapshot` (`scope_snapshot`, `scope_snapshot_id` are null; `scope_fingerprint` is empty). The durable Mission authorization snapshot instead binds the Owner, Mission, local-project target, workspace root, allowed actions/tools, and empty network/credential boundaries.

The previous restart validator required `scope_snapshot_id` in both the scope context and the authorization context. That requirement fits Missions using an external persisted ScopeStore snapshot, but cannot match the authenticated public local-project flow. As a result, it rejected a valid, integrity-checked `RESOURCE_BLOCKED` record despite the Windows artifact reporting Owner authorization and Scope Firewall checks as valid. This was a validator-shape mismatch, not a MissionStore persistence defect.

## Correction under review

`_mission_restart_authority_projection` now supports two explicit, non-interchangeable scope bindings:

1. **Public local-project workspace:** requires a nonempty `local-project:` target that matches the Mission authorization snapshot; exact workspace-only scope; the resolved project root must equal the authorization snapshot's workspace root; every planned action and `run_project_tests` must be within the public scope and Mission authorization allowlists; data boundary must name only that target; network and credential allowlists must be empty; the Mission authorization snapshot hash must verify; and the persisted Owner evidence, proof/approval fingerprint, session, request, policy and instruction fingerprints must agree. A scope ID appearing without its corresponding persisted scope object is rejected.

   Model-turn identities remain nonempty in this public flow: `authorization_context_id` is the verified Owner-evidence fingerprint, while `scope_snapshot_id` uses a deterministic `public-local-project-scope:<SHA-256>` over the exact persisted local scope dictionary when there is no external ScopeSnapshot row. This digest is a content binding only; it is not a fabricated external snapshot or an authority grant.

   The installed-app harness independently supplies the expected project ID and root to this check; the persisted target must match that ID and the resolved root must match the real project directory (`is_dir`). Public `allowed_tools` is re-derived from the stored Owner instruction using the same project-scope policy function, while both Mission authorization `allowed_tools` and `allowed_actions` must equal the planned actions plus the fixed Owner UI control-plane capabilities—no unplanned expansion is accepted. Owner attribution uses `OwnerAuthenticationEvidence.is_valid_for_active_session` as the cross-process fallback and checks the active session's Owner ID against the Mission identity. This is attribution only: it neither refreshes authorization nor resumes a Mission, and restart still requires Owner reauthentication.
2. **External persisted Owner ScopeSnapshot:** remains available only to generic restart-basis callers that do not supply an expected local-project ID/root. It now requires the scope ID to match the serialized context, the scope's `owner_session_id` to match the context session, and the same active Owner evidence/session/identity check. It cannot substitute for the public local-project binding in the installed-app acceptance path; when an expected local project is supplied, an external ScopeSnapshot is rejected.

The projection identifies which binding was verified. It does not grant authority, execute tools, resume a Mission, create evidence, or change the restart's Owner reauthentication requirement. Missing/corrupt Mission rows, bad integrity or authorization hashes, mismatched Mission/Owner/request/target/root, inactive or wrong-Owner sessions, expanded scope or either allowlist, added networks/credentials, malformed values, or contradictory execution records remain fail-closed.

The preflight record producers persist the truthful resource failure and `not_dispatched` checkpoint before returning. Both `MissionRuntime.run_slice` and the native model-turn process-sandbox preflight attach a deterministic `attempt_id` and explicit `attempt_source` (`mission_slice` or `model_turn`), with the identifiers available to that path. The same Mission/request/attempt identity and negative dispatch/process flags are carried through the failure, checkpoint, `FailureDetected`, `FailureDiagnosed`, and `RESOURCE_BLOCKED` transition. `MissionStore` covers the Mission payload with its integrity hash. No record is manufactured when no attempt occurred.

The restart-basis verifier recomputes the attempt identity and requires its Mission/request/source and blocked call/action/step bindings to agree across checkpoint, failure, events, transition, and relevant history. It verifies model-turn proposals and their durable `ToolCallResult` records against the same run/turn/plan/call/action/step IDs, and pairs each result with its exact proposal. The result's name, JSON-canonical arguments, Mission/request/run/turn/plan/action/step IDs, authorization-context ID, and scope-snapshot ID must match that proposal; those IDs must also be nonempty and equal the trusted Owner-evidence fingerprint and the authoritative external-scope ID or public-scope digest, not merely agree between two records. Each entry in a Mission tool-result ledger must match one of two narrowly defined schemas: a complete `ToolCallResult` with nonempty identity bindings to its Mission/request, or the exact `external_effect_reconciled` record written by Owner recovery. That recovery record is accepted only when its Mission/request, operation, task, success flag, error, terminal effect ID, and effect state match one unique, Owner-bound `SUCCEEDED`/`FAILED` effect-ledger entry; it is historical reconciliation, never evidence for the currently blocked call. Incomplete or orphan records fail closed. Every blocked model call must have exactly one negative result with the expected preflight error and an empty result payload; a missing, malformed, duplicated, positively dispatched, successful, or mismatched tool result fails closed. Repeated call IDs or record hashes are rejected both within one ledger and across distinct ledger locations; the preflight verifier does not deduplicate across sources. Any present success/dispatch/process-start marker must be the Boolean `false`; strings, integers, nulls, and other values are rejected rather than interpreted as negative. Within Action History, `ok` must likewise be Boolean `false` if present, and nested observation statuses indicating success—including `ok` or `verified`—are rejected. These rules apply recursively to the blocked action's observation fields. Mission-slice records also fail closed if a tool result appears bound to the blocked action. The validator checks the top-level, progress-level, and `model_loop` tool-result ledgers and includes their canonical digest in the restart projection.

The `effects` endpoint is now required for a preflight basis. Each effect must be well-formed and bound to the same Mission, request, and Owner; its operation must remain in the authorized tool allowlist; an effect for a blocked action, an effect linked to the blocked attempt, an unbound effect, or any effect requiring reconciliation rejects the basis. The full canonical effect-ledger digest is included in the before/after reconciliation projection, so later changes cannot be silently ignored. Candidate polling fetches this ledger whenever status is `RESOURCE_BLOCKED`; an unavailable or incomplete ledger remains `BLOCKED`. These checks do not infer process execution or success. Evidence from status is still checked against the separate evidence endpoint, and evidence attributed to the blocked attempt is rejected. A missing report is tolerated only as HTTP 404 for an already verified `RESOURCE_BLOCKED` Mission; the generic completed-execution reconciliation remains strict.

The installed-app harness waits within its existing bound for either a durable execution-chain basis or a valid terminal preflight-block basis before considering restart. If neither is present, it contains/pauses only, records `NOT_RUN`/`BLOCKED`, and does not restart or resume that Mission. For a terminal preflight block, the restart callback does not resume the Mission. A preflight basis marked `VERIFIED` means only that the truthful blocked record reconciled; the final gate still requires `GOAL_COMPLETED`, actual bounded project-test execution and evidence, a report, approvals, and required restart cycles. `READY`, `RESOURCE_BLOCKED`, missing evidence, or `NOT_PRESENT` execution chains cannot pass as success.

## Regression coverage

The acceptance-harness tests construct the actual public local-project scope shape without inventing an external ScopeSnapshot and verify both `mission_slice` and `model_turn` preflight records reconcile to the identical post-reopen projection. They prove fail-closed behavior for absent/wrong expected project bindings, a non-directory root, changed project target/root, expanded scope, extra public tool or Mission tool/action, missing tool allowlist, added network/credentials, Owner proof mismatch, invalid authorization hash, Owner-evidence request/session mismatch, inactive/wrong-Owner sessions, and an external scope presented for an expected local project. The public-scope regression now mirrors the bridge's actual contract: the persisted authorization lists equal the full original Owner-instruction-derived scope plus fixed UI control-plane capabilities, while the planned actions remain a strict subset; this prevents false rejection without expanding authority. New regressions tamper with or remove model-turn tool results, reject changed arguments/name/scope binding or empty authorization/scope IDs, and confirm that public scope digests change with scope content while persisted external IDs remain unchanged. They reject incomplete orphan ledgers missing a call ID, name, or run identity; reject string, integer, and null dispatch/success/process-start markers in results and Action History; reject non-false `ok` markers and nested Observation statuses claiming success, including `ok` and `verified`; reject an exact duplicate call across separate ledger locations as well as duplicates within one ledger; and accept the real reconciliation-record shape only when it is matched to a terminal effect. The general execution projection now preserves every source record instead of removing exact mirrors: duplicate call IDs across top-level and nested ledgers set the duplicate flag and fail project proof, including a duplicate of `run_project_tests`. They also reject missing/mismatched effect bindings and explicit `null` ledgers; remove or contradict the effect ledger; add an effect for the blocked action or an unresolved effect; and change a valid unrelated effect between restart snapshots to prove the ledger digest is reconciled. Candidate snapshots without the effect ledger remain blocked. Existing tampering tests continue to cover missing/corrupt records, invalid checkpoints/failures/events, mismatched attempt bindings, evidence disagreement, positive process-start flags, and untouched `READY` state.

The runtime regressions reopen MissionStore and switch the LLM while preserving the same truthful preflight failure and Owner/scope bindings without dispatch. The restart-quarantine tests preserve `OWNER_REAUTH_REQUIRED` and prevent automatic replay for nonterminal Missions. These are regression fixtures; they do not claim live Windows tool execution or successful project-test evidence.

## Guardrails retained

- Untouched `READY` Missions remain subject to `OWNER_REAUTH_REQUIRED` after restart and are never auto-resumed.
- Terminal `RESOURCE_BLOCKED` remains blocked, never becomes `GOAL_COMPLETED`, and is never represented as process start, evidence, or completion.
- Restart reconciliation requires integrity-checked, Mission-bound sources. Owner reauthentication does not turn missing, malformed, corrupt, or `NOT_PRESENT` sources into valid execution/evidence.
- Public project Missions are accepted only through their exact local workspace / Owner authorization bindings; scope is not broadened and recovery does not authorize tools.
- The Windows AppContainer backend remains unimplemented in the observed CI run. The final verdict must remain failing unless a subsequent Windows run proves actual authorized execution and independently bound evidence/result.
