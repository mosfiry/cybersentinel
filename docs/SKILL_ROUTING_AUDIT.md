# توجيه المهارات: ما أُخذ من reverse-skill وما رُفض

## النتيجة الهندسية

التحسين المستهدف هو **اختيار مهارة معتمدة ومناسبة، لا إنشاء منفّذ جديد**. يملك CyberSentinel أصلًا سجل مهارات مُراجعًا، ومخططًا يعتمد النموذج، وتنفيذًا محكومًا بالتفويض، وحفظًا واستئنافًا وأدلة. أُضيف فوق هذه البنية موجّه محلي حتمي اختياري لكل مهمة؛ لا يستدعي نموذجًا أو API، ولا يقرأ ملفات SKILL.md أو يشغّل إجراءاتها. عند التعادل أو غياب تطابق مؤهل يمتنع عن اختيار مهارة؛ يظل المخطط العادي خاضعًا للمصادقة والتفويض والنطاق.

المصدر المرجعي المفحوص مباشرةً هو [reverse-skill عند cab634bd855fc287f6e420c1f36fd1a6b9245960](https://github.com/zhaoxuya520/reverse-skill/tree/cab634bd855fc287f6e420c1f36fd1a6b9245960). لم تُنفذ سكربتاته أو اختباراته، ولم تثبت تبعياته. النتائج الأمنية أدناه استدلال من الشيفرة، وليست إثبات استغلال ديناميكي أو اعتمادًا على README والشارات.

## نتائج أمنية أثّرت في قرار الدمج

**لم يُنقل حارس التفويض النصي.** يضمّن `skills/scripts/case-init.sh:231–250` ونظيره PowerShell `:234–253` قيمة Hint مباشرة في Markdown، بينما يقرأ `case-guard.sh:42–112` ونظيره PowerShell `:33–86` أول الأقسام المطابقة. إدخال متعدد الأسطر قد يضع أقسام auth/scope/readiness مزيفة قبل الحقول الحقيقية. هذا مسار تزوير محتمل مستنتج ساكنًا، وليس استغلالًا منفذًا. كذلك لا تثبت أعلام CLI أو preset مثل `ctf-public` هوية صاحب الإذن أو نطاق الهدف الحقيقي.

**لم تُتبع تعليمات المهارات الخارجية.** يوجد تعارض بين شرط الموافقة في `RULES.md:7–15` وبين تعليمات التنفيذ الفوري في `skills/SKILL.md:9–17` ومهارات فرعية. النصوص الحرة كلها بيانات غير موثوقة؛ لا يمكنها تغيير سياسة النظام أو منح الصلاحيات أو إخراج الأسرار. في التنفيذ الجديد لا تدخل الأوصاف والإجراءات والأمثلة في حساب ترتيب المهارات أصلًا؛ الاسم والقدرات مدخلات تطابق فقط، وليست سلطة تنفيذ.

**لم يُنقل اكتشاف الأدوات المشغّل للبرامج.** `refresh-tool-index.sh:163–199` يشغّل أوامر إصدار برامج PATH، و`:236–316` يقرأ إعدادات ويفحص خدمات loopback. هذه آثار فعلية لا مجرد تعداد أسماء. الموجّه الجديد يقرأ سجل الأدوات المركزي المتاح للتخطيط، دون shell أو تحميل أو تثبيت أو فحص شبكة.

**لم يُنقل الدمج التلقائي للخبرات.** `.github/workflows/auto-merge-journal.yml:9–17,70–156` يمنح كتابة ويدمج محتوى بعد مرشحات نصية؛ regex لا يثبت خلو ذاكرة يقرأها الوكيل من حقن التعليمات. تبقى دورة التعلم الحالية في `api/skills.py` مبنية على مهمة مالك مكتملة وأدلة موثقة وموافقة صريحة؛ لا اعتماد تلقائي لسجل خارجي.

**لم تُنقل مسارات توجيه خارجية.** `master-route.sh:129–135` ونظيره PowerShell `:119–124` يبنيان مسار المهارة من config دون إثبات احتوائه داخل الجذر بعد canonicalization. الموجّه الجديد يعيد معرف سجل مهارة، لا مسارًا؛ لا يفتح هدفًا مستمدًا من النص ولا ينفذ أمرًا. تبقى حماية ملفات/أوامر الأدوات لدى حدود CyberSentinel القائمة.

## أين تبقى حدود النظام

`AgentCore.run_owner_mission` يصادق على جلسة المالك قبل الاختيار. يتطلب `auto_skill` قيمة boolean حقيقية ويرفض جمعه مع اختيار صريح. تؤهل المهارة فقط إذا كانت نسخة نشطة معتمدة لنفس هوية المالك، وتجتاز تحقق التعريف/التجزئة، وتتوفر أدواتها ويستوعبها النطاق ومتطلبات التخطيط. لا تتغير حدود ToolRegistry أو OwnerPolicy أو Scope Firewall بسبب نتيجة المطابقة.

يُعاد استخدام `bind_mission` ثم مطابقة الإصدار والتجزئة مع قرار التوجيه لمنع تبدل النسخة بين الاختيار والربط. تستخدم المهارة كإرشاد موسوم `UNTRUSTED_SKILL_GUIDANCE`، وليس كتعليمات نظام أو إجراءات آلية. يفحص التنفيذ الحالي السياق الحي والنسخة والتفويض والنطاق مجددًا قبل الإرسال؛ يتوقف عند الإلغاء أو تغير المرجع. لا تعاد المطابقة تلقائيًا عند الاستئناف، حتى لا تستبدل مهارة جديدة مرجعًا محفوظًا.

تُحفظ نتيجة التوجيه المحدودة في `mission.provenance.skill_routing`، والمرجع في `skill_binding` ضمن سلامة Mission الحالية. تبقى الخطوات والتقدم والأخطاء والأدلة وcheckpoints في المخازن الحالية. يستخدم مدير النماذج المحلي `agent/local_runtime/manager.py` وModelRouter دون اشتراط مزود مدفوع؛ اختبارات الميزة تستخدم مزودات حتمية محلية للاختبار وليست إثبات جودة نموذج محلي حي.

كشف اختبار استكمال فعلي بعد إعادة فتح المخزنين أن `MissionRuntime._skill_dispatch_scope` كان يفترض إصدار التفويض 1 عند اشتقاق الصلاحيات، رغم زيادة الإصدار بعد إعادة تفويض المالك. صُحح تمرير الإصدار المتوقع من metadata المهمة المتحقق منها إلى `DelegationScope.from_snapshot`؛ لم يُزل تحقق الإصدار أو البصمة أو المالك. يثبت اختبار سلبي مستقل أن اختلاف الإصدار المعلن عن اللقطة ما زال يُرفض. أُعيد فتح المخازن بإنشاء كائنات جديدة داخل عملية الاختبار نفسها؛ هذا ليس ادعاء إعادة تشغيل Windows أو قتل عملية تشغيل حقيقية خاصة بهذه الميزة. اختبارات process-death العامة القائمة تشغّلها مجموعة التراجع.

`OwnerSkillService` يبقى مسار التقديم والموافقة والإلغاء؛ الاسم أو كلمة Owner أو معرف مهارة ليس دليل هوية. تبقى أدوات الشبكة تحت scope resolver وpinned HTTP وdispatch gate، وأدوات الملفات/العمليات تحت workspace/sandbox الحاليين. قرار التوجيه لا يثبت سلامة الهدف، ولا يحاول استبدال أي من تلك الحدود.

## التراخيص والاعتماديات

الترخيص الجذري للمرجع MIT، لكن `CTF-Sandbox-Orchestrator/LICENSE` هو GPL-3.0، و`skills/pentest-tools/src-hunter/LICENSE` مستقل MIT. لا تُعامل الحزمة كلها كـMIT بلا استثناء. التنفيذ هنا تكييف للفكرة من الصفر، بلا نسخ ملفات أو كود أو حزم مرجعية، وبلا تبعيات جديدة أو تغييرات lockfiles. Bootstrap المرجعي يجمع pins/hashes لبعض البرامج مع مراجع متحركة لغيرها؛ لم يُعتمد أو يُشغل. فحص الأسرار المرجعي محدود وليس شهادة خلو شاملة.

## Windows وBlocker D

التحقق المحلي يتم على Linux؛ اختبارات JavaScript أو عقود Desktop ليست قبول Windows Installed UI. على SHA الأساس `bb1148f` نجح CI الخاص بـPython والعقد الأصلي وVHD وتجربة LowBox التشخيصية، بينما أخفق مثبت Windows وAppContainer وWorkers Builds. [قبول المثبت الأساسي](https://github.com/mosfiry/cybersentinel/actions/runs/39059554573) سجل `integrated_mission_did_not_reach_goal_completed:RESOURCE_BLOCKED`. [عقود Windows الأساسية](https://github.com/mosfiry/cybersentinel/actions/runs/39059554581) سجلت لفئة AppContainer: **17 نجاحًا و4 إخفاقات** عند `CreateProcessW LPAC (2)`.

النجاح في [تجربة LowBox](https://github.com/mosfiry/cybersentinel/actions/runs/39059554586) تشخيص فقط؛ عقدها يتطلب `mission_acceptance=BLOCKED` و`backend_enabled_by_slice=false`. لم تغير الميزة ذلك ولم تصلح الاحتواء الأصلي. **Blocker D غير محلول بهذه الميزة**. نتائج التنفيذ النهائية وأعدادها ونقطة الحفظ في `docs/SKILL_ROUTING_RESULTS.md`؛ لا يجوز استنتاج PASS شامل من نجاح اختبارات التوجيه وحدها.

## حدود قابلة للتحسين لاحقًا

المطابقة الحتمية كلمات كاملة وليست فهمًا دلاليًا؛ مرادفات أو لغات لا تتقاطع مع الاسم/القدرات قد لا تختار مهارة. الامتناع مقصود ولا يعطي إذنًا إضافيًا. تصفية الأدوات تمثل قائمة التخطيط الحالية وليست فحص صحة تشغيل كل تبعية؛ فشل الأداة بعد الاختيار يخضع للتعافي الحالي، لا إعادة توجيه صامتة توسع المهارة. حد الفهرس 500 رأس نشط؛ تجاوزه يجعل التوجيه غير متاح بدل اختيار نتيجة من فهرس مبتور. لا توجد ذاكرة خارجية أو فهرسة شبكة أو تنفيذ تثبيت آلي.

رُصد إخفاق يعتمد على ترتيب مجموعة أمنية مركزة على الفرع الجديد وعلى SHA الأساس نفسه: تترك ثلاثة اختبارات V9 لمحاكاة `BaseException` خيوط `mission-lease-keepalive` حية، ثم يكشفها التأكيد العام في `test_lease_fencing.py:204`. المجموعة المحددة سجلت 158 نجاحًا وإخفاقًا واحدًا على النسختين؛ الاختبار المنفرد نجح. عند فصل ملف crash في عملية pytest مستقلة نجحت مجموعة الأمن ذات الـ149 اختبارًا وملف V9 ذي الـ10 اختبارات. لم يُعدّل الاختبار أو يُحذف أو يُتخطَّ لتجميل النتيجة؛ نجاح التشغيل الكامل منفصل عن هذا الإخفاق الموروث القابل للإعادة. كما أن قراءة الفهرس عبر `registry._connect()` ارتباط صيانة خاص يمكن تحويله لاحقًا إلى واجهة قائمة نشطة عامة، دون أثر تفويض جديد.
