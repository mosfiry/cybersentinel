# Local AI Hardware Advisor

## Scope and trust boundary

The advisor is an extension of CyberSentinel's existing Electron Settings → Local Model Manager. Inference stays on the machine through the bundled `llama.cpp` CPU server, bound to loopback. It does not add paid inference APIs, API-key requirements, hosted inference, or a cloud fallback. Internet is used only to obtain catalog-pinned model/runtime artifacts and metadata. The packaged desktop target is Windows x64; Linux x64 is the separately exercised local acceptance target.

Only the bundled, curated, immutable catalog is installable. Search filters that catalog; arbitrary Hugging Face URLs, model repositories, executable model code, and unreviewed installer payloads are not trusted or installed. An unlisted candidate remains unsupported until its repository, immutable revision, exact GGUF file, hash, license, architecture, and backend are independently verified and added through a reviewed catalog change.

## What the scan measures

The read-only scan reports the OS/architecture, CPU model, logical CPUs, physical cores when a local OS probe succeeds, available instruction-set flags when exposed by the OS, installed and currently available RAM, a conservative inference-memory budget, model-volume free space, and GPU/driver/VRAM facts only when a local discovery method provides them. NVIDIA details come from `nvidia-smi`; on Windows, WMI may provide adapter name and driver only. WMI `AdapterRAM` is intentionally not trusted as dedicated VRAM. Shared GPU memory and unsupported/unknown measurements are reported as unavailable, not fabricated.

The safe inference budget reserves at least 2 GiB, or 10% of installed RAM when larger, from currently available RAM. The catalog's minimum/recommended RAM thresholds remain estimates; they are not measurements of token throughput, actual process RSS, temperature, or model quality. Free-disk eligibility reserves the exact model-file size plus 1 GiB. The scan does not create the selected storage directory, download a model, activate a runtime, or change settings.

## Recommendation interpretation

Recommendations are deterministic and hardware-gated. The three distinct roles are overall balance, coding/engineering fit, and reasoning-oriented strongest practical choice. They use the curated catalog's parameter size, quantization, estimated memory, file/disk size, context cap, CPU fit, and upstream model-card capability descriptions. Stable model-ID tie-breaking makes identical inputs produce identical ordering. Scores are explicitly catalog-based heuristics, not benchmark results. If fewer than three distinct models qualify, the advisor returns only those candidates and explains why; no compatibility threshold is lowered to fill slots.

Each recommendation includes its exact quantization, pinned repository and 40-character revision, filename, catalog SHA-256, size, required disk margin, RAM estimate, CPU-only backend and supported OS/architecture, application context limit, license metadata, evidence basis, confidence, reasons, and limitations. Download is user-initiated; activation re-runs compatibility and integrity checks. Download cancellation leaves an uninstalled partial file resumable; it never makes a partial artifact activatable.

## GLM-5.3-Flash EXL3 offload assessment

GLM-5.3-Flash is **not installable or supported** by the current CyberSentinel runtime. It is retained only as an unsupported/experimental future-candidate note. The local catalog accepts a single `.gguf` file; the bundled runtime is llama.cpp CPU and has no EXL3/ExLlamaV3 adapter, no EXL3 metadata/download flow, and no Windows acceptance path for this model.

The project [`sybil-solutions/glm53-flash-offload`](https://github.com/sybil-solutions/glm53-flash-offload) and its linked implementation [`glm-flash-lite`](https://github.com/sybil-solutions/glm-flash-lite) were inspected at the source level. Its [results](https://github.com/sybil-solutions/glm-flash-lite/blob/main/docs/results.md) and [implementation notes](https://github.com/sybil-solutions/glm-flash-lite/blob/main/docs/how-it-works.md) report an EXL3 3.05 bpw checkpoint around **125.3 GB** (decimal) and measured modes on a specific RTX 3090 24 GB / EPYC 7443P reference host with 503 GiB RAM. The reported `fast` result is approximately **218 GiB free host RAM**; `exact` is approximately **111 GiB**; NVMe mode uses a **55 GiB** RAM cap and a separate approximately **117.3 GB** (decimal) packed expert store. The setup guide's recommended minima are more conservative (about 240 GB free for `fast`, 120 GB for `exact`, plus a 24 GB GPU); these results are not universal guarantees or a reproduced benchmark.

The published [setup guide](https://github.com/sybil-solutions/glm-flash-lite/blob/main/skills/glm53-offload-setup/SKILL.md), [Dockerfile](https://github.com/sybil-solutions/glm-flash-lite/blob/main/docker/Dockerfile), and [entrypoint](https://github.com/sybil-solutions/glm-flash-lite/blob/main/docker/entrypoint.sh) show a Linux/CUDA/SGLang/ExLlamaV3 deployment relying on Linux shell, `nvidia-smi`, `/proc`, cgroups, and (for NVMe mode) direct-I/O filesystem behavior. This does not establish a secure, supported Windows-native CyberSentinel path. Upstream ExLlamaV3 installation references to Windows do not supply this project's custom offload implementation or CyberSentinel integration. No Linux/Docker stack is added to the Windows installer.

## Verification limits

Unit tests use mocked hardware. A separate local scan on test hardware must be reported as observation, not as a Windows result. Real inference acceptance must report the exact platform, model revision/hash, runtime revision/hash, and whether inference was actually run. Source inspection, a passing fake-runtime unit test, or a downloaded weight file alone does not establish successful model support. Windows interactive installation must not be claimed unless performed on Windows.


## Unlisted-model review workflow

Settings also accepts a Hugging Face `namespace/model` identifier and a full 40-character lowercase commit SHA for a **metadata-only review**. The reviewer calls the fixed HTTPS `huggingface.co` model-revision API, confirms the resolved commit, and reports public GGUF filenames, filename-derived quantization, published sizes, model-card license declaration, and Hub LFS SHA-256 values where present. It does not fetch weights, use credentials, execute repository code, or add the candidate to the installable catalog. A Hub-declared LFS digest is evidence, not an independently verified product pin.

Unlisted candidates deliberately remain **not installable** in this build. The reviewer cannot establish GGUF header architecture from the Hub's model-list response, prove that the bundled Windows llama.cpp CPU binary supports that architecture, independently pin/test the candidate artifact, or perform maintainer curation. Those specific gates are returned to the user; only adding an exact reviewed artifact to the built-in catalog can make it installable. The existing search still exposes every curated entry, including entries outside the top-three recommendations.

Sources for the metadata shape and lookup behavior: [Hugging Face Hub API client reference](https://huggingface.co/docs/huggingface_hub/en/package_reference/hf_api) (model info with `revision` and file metadata such as size/LFS information) and [Hub API endpoint overview](https://huggingface.co/docs/hub/api). The exact immutable revision endpoint and `blobs=true` response were also checked against the already-pinned Qwen3-4B GGUF repository during implementation; this was a metadata request only, not a weight download.


## Actual test-hardware acceptance — 2026-10-09

A fresh read-only scan on the available Linux x86_64 test host measured an Intel Xeon Processor at 2.50 GHz, 8 logical / 4 physical cores, 23.6 GiB installed RAM, 21.2 GiB available RAM, an 18.8 GiB conservative inference budget, and 8.5 GiB free on the model-storage volume. It exposed AVX/AVX2 and related x86 flags from `/proc/cpuinfo`; no GPU discovery tool was available, so GPU/VRAM/shared-memory facts remained unknown. These are host observations, not Windows results or performance benchmarks.

The repository's isolated acceptance harness completed with **PASS** on that Linux CPU path. It downloaded the exact `qwen3-4b-q4-k-m` file (`unsloth/Qwen3-4B-GGUF`, revision `22c9fc8a8c7700b76a1789366280a6a5a1ad1120`, 2,497,281,312 bytes, SHA-256 `f6f851777709861056efcdad3af01da38b31223a3ba26e61a4f8bf3a2195813a`) and the pinned llama.cpp `b11146` Ubuntu x64 CPU archive (16,998,357 bytes, SHA-256 `c150306eb16b5ab696f76a8bdf810c35fd98a24e82158742e6fa28f420ff8410`; verified server-binary SHA-256 `22de090746c114569367998ec930b28f27f12e078e593ff21175a54b409d26fe`). Direct inference returned the expected marker through the sole `local_llama_cpp` provider. An isolated Owner-authenticated AgentCore Mission then reached `GOAL_COMPLETED` with six provider-bound turns, five successful read-only `status` calls, a text-only final response, validated status-snapshot evidence, an intact trajectory hash chain after reopening its temporary store, and verified runtime shutdown. The structured harness result contains digests and counts only; no prompts or model/tool response bodies are retained.

All downloaded model, Mission-store, and runtime artifacts were temporary; the harness removed its isolated model/Mission storage after success. No application profile or persistent active-model setting was changed. This confirms the tested Linux CPU path only. Native Windows installer execution and Windows interactive acceptance still require the Windows workflow; no Windows/GPU acceptance or throughput benchmark is claimed.
